# HIIT (implemented 2026-07-20; saved routines + export/import added 2026-08-04)

A circuit/interval builder that runs on top of the existing lift and cardio backends rather than being its own logging system — a HIIT workout, once saved, produces exactly the same `lift_sets`/`cardio_entries` rows a normal log-set form would, just interleaved with other exercises and rest periods along the way. The user's own framing: "it can be a circuit... but we are setting it up like a group of workouts so they have the needed flexibility."

## Data model

Two new tables, no changes to existing ones (lift/cardio logging is reused as-is at save time).

**`hiit_sessions`** — one row per HIIT workout. Beyond the usual date/notes/started/completed/status shape (mirroring `PlannedSession`), it carries **live resume state**: `current_sequence_index`, `current_phase` ('work'/'rest'), `phase_started_at`, `phase_remaining_seconds`, `current_reps_remaining`, `paused`. Nothing about an in-progress session lives only in memory — leaving the active-session screen (Pause, or just navigating away without pausing) and coming back later through Home's HIIT card resumes exactly where it left off, because every state change is written immediately, not just held in a `State` object that would be lost on screen disposal.

**`hiit_slots`** — one row per exercise occurrence, in strict global order (`sequence_index`), tagged with which round it belongs to (`group_index`, purely for the progress bar's round markers and for knowing where a round's rest goes). Each carries its **target** (`target_type`: reps/amrap/time/distance, `target_value`, optional `weight`) set once at setup and never edited live, and its **actual** result (`actual_reps`/`actual_weight`/`actual_time_seconds`/`actual_distance`/`actual_load`) filled in as the session runs (or assumed-equal-to-target and left for the report screen to correct, for cardio). `rest_after_seconds` covers both the gap to the next slot in the same round *and* the gap between rounds — whichever slot happens to be last in a round just carries the round's rest value, so there's no separate "round" table needed. `lift_set_id`/`cardio_entry_id` columns exist but are **not populated in v1** — see "Known gaps."

No `hiit_routines`/saved-template table yet — per the user's own call ("I like this but I want to get the main idea down first") — every session is built from scratch in `HiitSetupScreen`. Aborting doesn't lose the routine though: the setup screen accepts optional `seedSlots`/`seedAutomatic` and `HiitActiveScreen._abort` hands its exact in-progress shape back rather than making the user rebuild it.

## The setup screen (`HiitSetupScreen`)

A routine is a list of **rounds** (`_GroupDraft`, in-memory only until Start is pressed), each a list of **exercises** (`_SlotDraft`). Building it:
- **"Add exercise"** inside a round appends a blank slot to that round (`ExercisePickerField`, any lift or cardio exercise — no pinned-only shortlist the way lift logging has, since picking for a routine isn't the "usual suspects" case that optimization is for).
- **Per-slot target**, shape depends on the exercise kind:
  - Lift: **Reps** (a fixed count) or **AMRAP** (as many reps as possible within a time cap — picking AMRAP reveals the time field, replacing the reps field). Weight is optional either way.
  - Cardio: **Time** or **Distance** (entered/shown in that exercise's own `DistanceUnit`, same per-exercise-unit system cardio logging already uses). "Resistance (optional)" reuses the same generic unitless field cardio logging has.
- **Rest** between any two slots (within a round) or between rounds is "Direct" (no rest, immediately continue) or a rest duration in seconds — a small inline control after each slot (`Then: Direct | Rest __s`), and a more prominent centered one between round cards (`Between rounds: ...`) matching how the mockup visually distinguished the two.
- **"Add another round"** duplicates the *last* round wholesale (same shape as adding another logged set) so tweaking weight/reps for round 2 doesn't mean rebuilding it — the user's own words: "the + duplicates the above group like how adding a new set does so things can be further edited."
- **Automatic vs. manual** — one switch at the top, governs the whole session (see below), not per-slot. **Defaults OFF (manual)** — the user's own call after trying both: "it works a bit better that way."
- **Sessions start running immediately.** The very first `HiitSession` row is created with `paused: false` and `phaseStartedAt` set to the moment Start was pressed — no separate tap-to-begin step. (An earlier version started paused, as an implicit lesson in the pause/resume interaction — reverted per the user's own follow-up: "it seems to be paused and I have to unpause it... make sure it starts right away.")
- **Preset routines** (`hiit_presets.dart`) — a small hardcoded starting-point library, reachable via a menu icon (`Icons.auto_awesome_outlined`) in the setup AppBar's top-right, next to the "Set Up HIIT" title. Tapping it lists each preset by name; picking one replaces the current draft (`_groups`/`_automatic`) with that preset's rounds — confirming first if the draft already has anything built, since it's a full replace, not a merge. A `HiitPreset` is keyed by exercise *name*, not id (presets are hardcoded before any particular install's exercise ids exist), resolved against the currently loaded `_allExercises` at apply time; a name that doesn't resolve (a custom library missing a seeded exercise) is silently skipped rather than crashing, same convention the rest of these screens use for missing lookups. Three shipped:
  - **Full-Body AMRAP Ladder** — Push Up, Walking Lunge, Dumbbell Curl, all AMRAP, 3 rounds stepping 20s → 30s → 40s (an actual ascending "ladder," not just three identical rounds).
  - **Beginner Intro Circuit** — Push Up, Walking Lunge (light rep targets), then Stairs (2-minute time target) as a cardio finisher, 2 rounds, generous rest.
  - **Arm Day Dumbbell Circuit** — Dumbbell Curl, Hammer Curl, Lateral Raise, Preacher Curl, reps-based, 3 rounds, direct transitions within a round (giant-set style) with rest only between rounds.

  No saved/user-defined routine templates yet (still the "get the main idea down first" scope boundary — see "Known gaps"), and no pinning of past sessions as quasi-presets yet either — floated as a future idea but not built; Redo (above) is today's way to reach a past routine.

## The active session (`HiitActiveScreen`)

One slot at a time, each a **work phase** (the exercise itself) optionally followed by a **rest/transition phase** (if that slot's `restAfterSeconds` is set). `CountdownRing` (new widget, `lib/widgets/`, adapted from `WeekRings`' small ring painter but much bigger and doubling as the button) is the centerpiece:
- **Reps target**: ring shows "N left," center tap decrements. Once it hits 0, the button becomes "Next."
- **AMRAP/Time target**: ring shows a countdown ("3:15"), non-tappable while running, becomes "Next" at 0. AMRAP-specific: in **manual mode only**, a small "+1" counter row appears below the ring so reps-done can be tracked live while the clock runs — in automatic mode that number isn't tracked live at all, it's filled in afterward on the report screen (the user's own resolution: "if in automatic mode then they can track these numbers at the end in the report").
- **Distance target**: there's no way to auto-detect distance covered, so this phase is always a manual "tap when done" regardless of the automatic/manual setting, with the ring counting *up* (elapsed time) rather than down, purely for reference.
- **Rest/transition phase**: same countdown-ring mechanic, title "Transition," detail "Next: <upcoming exercise>" so there's a moment to prep — matches the mockup exactly.

**Automatic vs. manual** (confirmed with the user before building, since guessing wrong here means rebuilding the whole state machine): the global toggle governs whether reaching a phase's goal (timer hits 0, or reps counted down to 0) **auto-advances** to the next phase, or just flips the center button to "Next" and waits for a tap. This applies uniformly to work phases and rest phases — a rest gap always shows a live countdown in *both* modes (confirmed with the user), it just differs in whether hitting 0 moves on by itself or waits.

**Progress bar** — one segment per slot (not per phase), filled/half-filled/empty by position, with a wider gap marking round boundaries — "dots or lines... where the repeat points are," per the ask. The exercise/phase title (e.g. "Run", "Deadlift", or "Transition") sits centered directly below this bar, large (`AppText.bigNumber` at 32pt) and bold so it's readable without looking closely mid-set; the details line underneath it (weight/reps/etc., or "Next: <exercise>" during a transition) is similarly enlarged (20pt, semi-bold) — smaller than the title but noticeably bigger than normal body text.

**Pausing and resuming** — Pause freezes the current phase's countdown by snapshotting `phaseRemainingSeconds` and clearing `phaseStartedAt` (the live countdown formula becomes a no-op while frozen); Resume sets a fresh `phaseStartedAt` and continues from that snapshot. This is genuinely persisted (not just an in-memory `Stopwatch`), so leaving the screen entirely and coming back later through Home's HIIT card resumes correctly. A whole-workout elapsed-time display was scoped out of v1 (see "Known gaps") — pausing only needs to freeze the *current phase's* timer, which is what actually matters for correctness.

Three ways to trigger a pause, since "leaving the page" can happen a few different ways:
1. The **Pause button** itself (unchanged).
2. **Backgrounding the app or going to Home** — `HiitActiveScreen` observes `WidgetsBindingObserver.didChangeAppLifecycleState` and auto-pauses on `.paused`/`.detached` (deliberately not `.inactive`, which also fires for transient things like a system dialog and would false-trigger).
3. **The system back button/gesture** — the AppBar's own back arrow is hidden while the session is running and only appears once already paused, but the hardware/gesture back button bypasses the AppBar entirely. Handled via `PopScope(canPop: session.paused, ...)`: the first back-press while active pauses instead of leaving; a second press, now that it's paused, actually pops.

**Screen stays awake while active.** `wakelock_plus` is enabled in `HiitActiveScreen.initState` and disabled in `dispose` — scoped to exactly this screen, so setup and the report/review screen behave normally (allowed to sleep) and only the live countdown/rep-tracking screen keeps the display on.

**Abort** confirms, deletes the `hiit_sessions`/`hiit_slots` rows (nothing gets logged), and hands the routine's exact shape back to a fresh `HiitSetupScreen` via `seedSlots` so adjusting and restarting doesn't mean starting over. **Slots are locked in once started** — no reordering or skipping mid-session, per the user's own call ("they would need to abort or fudge it on their own if they wanted that").

## The report screen (`HiitReportScreen`)

Shown once the last slot finishes. The app **assumes every target was hit exactly as set** (weight, reps, distance, time) — this page is where that gets corrected: dropped weight partway through, cut a run short, didn't finish an AMRAP's reps. Same per-exercise-kind field editors as setup, just editing `actual*` instead of `target*`, pre-filled from whatever the active session already recorded (or the target value, for anything assumed-hit). A notes field, then **Save**:
1. Groups all slots by `exercise_id` (preserving round order).
2. For each exercise, one `AppServices.lifts.logSession`/`AppServices.cardio.logSession` call for the day — **one `LiftSet`/`CardioEntry` per round that exercise appeared in**, so curls done in round 1 and round 3 end up as two sets on one session, exactly like manually logging two sets would. This is what the user meant by "it tracks all the parts just like a lift... but to the HIIT it would track and know that they are really split with other stuff in between" — the *display* (Workouts tab) still shows it as one HIIT-grouped block, but the underlying data is indistinguishable from normal logging.

**Re-editing an already-saved HIIT workout** (`isEditingExisting: true`, reached via the pencil icon on a HIIT block in the Workouts tab — see below) reuses this exact same screen and layout rather than a separate "view" screen, just with a different Save behavior: instead of blindly calling `logSession` again (which would append a duplicate set/entry on top of what's already logged), it searches `AppServices.lifts.getSessionsForExercise`/`AppServices.cardio.getSessionsForExercise` for a same-date session per exercise and calls `replaceSets`/`replaceEntries` on it if found, falling back to `logSession` only if no matching session exists yet — the same `(date, exercise_id)` matching convention already used for Workouts-tab grouping. The AppBar title switches to "Edit HIIT Workout," and Save pops back to the Workouts tab instead of unwinding to Home.

**Redo** (`Icons.replay` in the AppBar, shown only when `isEditingExisting`) reopens `HiitSetupScreen` pre-filled with this workout's exact routine (`seedSlots`/`seedAutomatic`, the same mechanism `HiitActiveScreen._abort` uses) so an old session can be run again with tweaks — add a rep, bump the weight — instead of rebuilt from scratch. Entirely non-destructive: the original session's logged data is untouched; starting the redo creates a brand-new `hiit_sessions` row, unrelated to the one being viewed.

## Showing up in the Workouts tab

`LiftsScreen`'s Workouts tab already groups a day's lift sessions under their Workout Planner day (`WorkoutPlanService.assignToSessions`, movement-pattern-based matching). HIIT sessions don't have movement-pattern slots to match against, but they do know **exactly** which exercises they used (`hiit_slots.exercise_id`) — so the same day's un-grouped-by-planner lift sessions get a second matching pass: any lift session whose exercise id appears in a same-date HIIT session's slot list gets folded under a "HIIT Workout" header (same visual treatment as a Workout Planner day group — accent-tinted card, left accent bar) instead of showing as a loose entry.

**Cardio gets the identical second pass.** `LiftsScreen._load` now also fetches `AppServices.cardio.getAllSessions()`; for each date, any cardio session whose exercise id appears in a same-date HIIT session's slot list is grouped into that HIIT block too (`hiitCardioGrouped`, rendered via a new `_CardioWorkoutRow` — same card shape as `_WorkoutRow`, including the identical RPE-tinted accent bar in place of a leading icon, with a distance/duration summary line where a lift row shows "N sets · top weight"). A HIIT header shows up even for a HIIT session with **only** cardio slots and no lift sessions that day (`hiitWithAnything`, the union of `hiitGrouped.keys` and `hiitCardioGrouped.keys` — previously the header's existence depended entirely on `hiitGrouped`, so a lift-free HIIT workout wouldn't render at all). Tapping a cardio row's edit pencil opens `EditCardioSessionForm` in a bottom sheet, same as it would from Cardio Detail's own history. Cardio sessions *not* tied to any HIIT workout still don't show in this tab — that's the pre-existing, separately-scoped gap noted in `11_SCREEN_cardio.md` (the tab stays lift/HIIT-day-grouping only outside of a HIIT block), not something this fix addresses.

Individual exercise rows (`_WorkoutRow`/`_CardioWorkoutRow`) never carry a leading icon — only the *block* header does (`Icons.bolt` HIIT / `Icons.fitness_center` planned). `_CardioWorkoutRow` originally had its own `Icons.directions_run` on every row, which read as noisy clutter once a block could contain several rows; removed in favor of the same intensity-tinted accent bar `_WorkoutRow` already uses (keyed off `CardioSessionWithEntries.avgRpe` instead of a lift session's).

**HIIT and Workout Planner blocks are the same underlying widget** (`_GroupedWorkoutBlock` in `lifts_screen.dart`) — a tappable header (icon + title + edit pencil), an optional notes line, then the rows logged under it. They started as two independently hand-coded `Container`s, which is how the HIIT block ended up showing `hiit.notes` while the identically-shaped planned block silently never rendered `planned.notes` — the two just drifted apart in code that looked the same but wasn't actually shared. Unified into one widget so a fix or feature added to one (notes, future affordances) can't accidentally apply to only one block again. The only per-kind differences are the icon (`Icons.bolt` HIIT / `Icons.fitness_center` planned), the title text, and the `onTap` handler (`_editHiitSession` opens `HiitReportScreen(isEditingExisting: true)`; `_editPlannedSession` opens `ActiveDayScreen`).

## Saved routines, and friendly export/import (2026-08-04)

**Saving a routine** (`HiitSetupScreen`'s Save icon, `Icons.save_outlined`) is the deliberate, named "I want to keep this" path — distinct from the hardcoded presets above and from Abort's unnamed exact-draft-hand-back (both untouched, both still exist). Prompts for a name; a name that already matches a saved routine asks to overwrite (delete-and-reinsert its slots — safe, since a saved routine has no history depending on it, unlike a Workout Plan template's days) rather than silently creating a duplicate. New tables `hiit_routines`/`hiit_routine_slots` (`lib/data/repositories/hiit_routine_repository.dart`) — the target-only subset of `hiit_slots`' columns, since a saved routine has no `actual*` result yet.

**Loading** merges saved routines into the same picker the 3 hardcoded presets already used (`Icons.list_alt_outlined`, was `Icons.auto_awesome_outlined` — changed to read as one shared "pick a saved thing from a list" affordance with the Workout Planner's new Switch Plan action, `10_WORKOUT_PLANNER.md`), sectioned "Your routines" above "Presets."

**Friendly Excel export/import** (`lib/services/plan_export_service.dart`, `lib/widgets/plan_import_review_sheet.dart`) is a second, deliberately different format from Settings' raw whole-app backup (`BackupService`) — exercise **names**, never ids, so a hand-edited file stays readable; one sheet per saved routine, named after it, with bold round/column headers and an italic grey notes row explaining the layout. Export (`Icons.upload_outlined`) shares the generated file via the OS share sheet, same as Settings' export. Import (`Icons.download_outlined`) uses the same native file picker Settings' import already does (browse phone/Drive/anywhere, not a path field), parses every sheet, and shows a review bottom sheet — one row per sheet, Add (always creates a new entry, auto-suffixing the name on a collision) vs. Replace (default when a routine of that name already exists), plus any exercise name that didn't match anything in this install, skipped and listed rather than silently dropped or failing the whole sheet. Nothing writes to the database until Confirm. A first pass — expected to be refined once real exported files get reviewed.

## Demo data

`TestDataService._loadHiitData` seeds three past completed HIIT workouts (3 days ago, ~2 weeks ago, ~5 weeks ago) with deliberately different shapes — a reps+distance circuit, an AMRAP+timed-cardio circuit, and a reps+distance pairing with one deliberate shortfall (actual under target, exercising the report screen's "correct what didn't go to plan" case) — so the Workouts tab's HIIT blocks, the redo flow, and cardio-in-HIIT display all have real variety to review instead of only ever a session just finished. Deliberately uses exercises (`Dumbbell Curl`, `Walking Lunge`, `Good Morning`, `Ruck`) that the rest of the demo generator never touches, so a HIIT demo session never accidentally shares a (date, exercise) pair with the plain daily lift/cardio demo data — that collision would make the Workouts tab's date+exercise-id HIIT-matching fold unrelated sessions into the wrong block.

## Known gaps / deliberate scope boundaries
- **Cardio outside a HIIT workout still doesn't show in the Workouts tab.** A HIIT routine's own cardio slots now display correctly folded into their HIIT block (see "Showing up in the Workouts tab" above), but a plain, non-HIIT cardio session still doesn't appear in this tab at all — a pre-existing gap noted in `11_SCREEN_cardio.md`, unrelated to HIIT (still fully visible on that exercise's own Cardio Detail page). Revisit once cardio joins the Workouts tab generally.
- **`hiit_slots.lift_set_id`/`cardio_entry_id` are unused in v1.** Grouping is matched by (date, exercise id) instead of a direct FK, since `LiftRepository.logSession`/`CardioRepository.logSession` don't currently return the individual set/entry ids they create. Precise enough for display purposes; would need those repositories to return ids if a future feature needs the exact link.
- **No saved/reusable routine templates** — ~~explicitly deferred by the user ("get the main idea down first")~~ implemented 2026-08-04, see "Saved routines, and friendly export/import" above.
- **No live weight editing mid-session** — deliberately deferred too ("this may be something we add later with the pause button but for now we can skip live editing"), so weight/target edits only happen at setup or on the report screen, never while a set is actively running.
- **No whole-workout elapsed-time display** — only the *current phase's* countdown is shown; a separate "how long has this whole HIIT session taken" clock (with its own pause-aware accounting) wasn't in the mockup and was cut to keep the state machine's scope contained.
- **Distance-target slots don't validate against the preset** — there's no way to auto-detect distance covered mid-workout, so the ring just counts elapsed time up for reference and the actual distance is assumed-hit unless corrected on the report page.
