# Screen: Metrics

Home for all the non-lift logs. Two tabs: **Overview** (the original card-per-metric layout below) and **Days**.

## Days tab — implemented
Added after real use surfaced a real gap: a mistyped bodyweight (or steps/sleep/soreness) entry had no fix path short of wiping data. Mirrors the Lifts screen's "Workouts" tab — every logged entry (bodyweight, steps, sleep, soreness; explicitly **not** cycle entries, which stay confined to their own nondescript surface) grouped by date, most recent day first, each row with an icon (balance scale for weight, footstep icon for steps, bed for sleep, flame for soreness), a value, and an edit pencil.
- **Soreness rows** collapse to **one row per day**, not one per entry — all regions logged that day show as tags on a single "Soreness (Legs) (Chest) ..." row (revised after the user pointed out one-row-per-region cluttered the list). Tapping it reopens the full `SorenessBodyMapForm` tap-the-body-map sheet, pre-set to that day (`initialDate`), so every region can be corrected part-by-part in the same familiar UI used for logging, rather than a separate single-region dialog.
- **Weight/steps/sleep rows** reuse `LogSimpleMetricForm` in a new edit mode (`editingId` + prefilled value/date) that updates the existing row in place instead of inserting a new one — `MetricsRepository.update` / `BodyweightRepository.update`, both new.
- Respects the **Hide weight numbers** setting (`06_SCREEN_settings.md`) same as everywhere else — weight rows mask to "---lb" when it's on; you can still tap through to edit (the edit form always shows the real number, since you need it to fix it).
- **Custom metric rows (implemented 2026-07-17)** — one row per logged entry (not collapsed per day like soreness, since there's no shared multi-region sheet to reopen; each entry stands on its own), icon a plain `Icons.insights` (a custom metric doesn't have one consistent icon the way built-ins do — scale-kind metrics carry their own icon choice, but number/classes don't), value via `CustomMetric.formatValue`. Tapping the pencil opens `CustomMetricEntrySheet` with a new `editingEntry` param — same sheet used to log a new value, just pre-filled and doing a delete-then-insert of that specific row on save (handles a changed date the same way a fresh log would, no separate branch needed) rather than the once-per-day-replace logic `upsertEntry` uses for new entries.

## Overview tab — implemented (cards)
**Point-computation shared with Home (2026-07-19).** The per-metric chart-point/formatter logic (raw entries for Steps/Sleep, weekly-averaged for Weight, derived duration for Workout Duration, the classes-aware y-label formatter for custom metrics) moved out of `MetricsScreen` into `MetricChartPoints` (`lib/services/metric_chart_points.dart`) so Home's new Metric Trend cards (`02_SCREEN_home.md`) can show "Steps," "Sleep," etc. without a second implementation of the same math. `MetricsScreen`'s own methods are now one-line wrappers around it — no behavior change here, purely a same-code extraction.

**Notebook + "+" icons on the built-in cards (2026-07-17).** Steps, Sleep, and Weight each gained the same icon pair the custom metric cards already have: a notebook icon and a "+" icon in the card header. "+" opens the same `LogSimpleMetricForm` the quick-log FAB uses, in add mode, skipping the FAB's type picker since the card already says which metric this is. **No trash icon on any of these** — unlike a custom metric (where the whole definition is user-created and deletable), a built-in metric *type* can't be removed, only its individual entries can (via the notebook popup's own edit hooks, below).

**Notebook opens a per-metric popup, not the Days tab (revised same day).** First version pointed the notebook icon at the Days tab (`TabController.animateTo(1)`), reasoning that Steps/Sleep/Weight already had full browse/edit coverage there. The user's explicit call after seeing it: "much less intuitive, but I like that there's an easy place to see all the exact numbers/tags" — she wants a focused single-metric list, not the Days tab's everything-mixed-by-date view, even though it's a less discoverable interaction pattern. `MetricHistorySheet` (`screens/metrics/metric_history_sheet.dart`) is a new generic popup — a date + value/tags list, newest first, with an optional per-row edit pencil (`MetricHistoryRow.onEdit`, `null` skips the pencil) — used by **every** metric card, not just the three above:
- **Steps / Sleep / Weight** — date + value, edit opens the same `LogSimpleMetricForm` edit mode the Days tab already used.
- **Soreness** — previously had no header icons at all (the whole card just opened the body-map form). Gained a small header row (title + notebook) without disturbing the existing whole-card tap; its popup groups entries per day into tags (`"Quads (3)"` style, matching the Days tab's soreness collapsing), edit reopens `SorenessBodyMapForm` for that day.
- **Workout Duration** — gained a notebook icon (still no "+", still derived/nothing to add) showing date + computed minutes, no edit hook on any row since there's no single stored entry behind a derived number to correct.
- **Custom metrics** — unchanged, still `CustomMetricHistorySheet` (a separate, slightly richer widget with inline add + delete, not just this generic view-only one) — no need to unify, it already matches the same "focused popup, not a tab" spirit.
`MetricHistorySheet` is deliberately view-plus-edit-only, no delete — these are real logged history (not a disposable custom metric a user might have mis-built), so deletion still only happens through each metric's own existing flow rather than a new generic deletion path.
- **Steps** — `LabeledTrendChart`, 6-month cap, prediction extension on.
- **Sleep (hrs)** — `LabeledTrendChart`, 6-month cap, no prediction extension (not one of the "things with predictions" yet).
- **Workout Duration (min)** — `LabeledTrendChart`, one point per date, no prediction extension. **Derived, not manually logged** — unlike steps/sleep/weight there's no entry form for this; `TrendEngine.workoutDurationMinutesByDate` sums `lift_sessions.completed_at − started_at` per date across every logged session that day. Only counts sessions where both timestamps are set (i.e. "Track time" was on when logging, `04_SCREEN_quick_log.md`) — a session logged with tracking off just doesn't contribute a data point that day, it isn't treated as 0 minutes. A non-positive duration (clock skew/bad data) is dropped the same way. Covered by `trend_engine_test.dart`.
  - **Bug found on-device (2026-07-17): a lift-session sum can badly undercount the real workout.** A lift session's Track Time only measures how long *that logging form* stayed open — if sets get entered in a quick burst after actually finishing (or spread thin across the day), the sum reads far shorter than the real workout, which is exactly what happened ("tracked as like 15 mins but it was much longer"). Fixed by giving a completed Workout Planner session's own start-to-complete span priority: `workoutDurationMinutesByDate` now takes an optional `plannedSessions` param, and for any date with a completed `PlannedSession`, that session's duration **overrides** the lift-session sum for that date rather than adding to it (`ActiveDayScreen`'s own start-active/complete lifecycle was already correct — see `10_WORKOUT_PLANNER.md` — it just wasn't feeding this chart before). Dates with no planned session still fall back to the lift-session sum, same as before.
- **Soreness** — replaced the trend chart with a small non-interactive body-heatmap preview (front + back side by side) showing each region's most recent 0-5 level; tapping the card opens the same body-map logging sheet used from the FAB. See `00_UX_DESIGN.md` "Soreness body map."

### Resolved — Metrics soreness preview refresh bug
Was a real bug, not a timing illusion: `MetricsRepository.getByType` ordered only by `date DESC`, with no tiebreaker for multiple same-day entries. Logging soreness twice in one day (e.g. morning + evening — the user's actual pattern, since their DOMS often peaks ~36h post-training and can meaningfully shift within a day) meant SQLite fell back to insertion order for the tie, so the **first** entry of the day kept winning over a later same-day correction, until the calendar date rolled over. Fixed with `orderBy: 'date DESC, logged_at DESC, id DESC'`. This wasn't just a display glitch — `ReadinessEngine.computeMuscleReadiness`'s soreness factor reads through the same `getLatest()` path, so the readiness compass had been silently using stale same-day soreness too.

**Multiple entries per day: kept, not collapsed to one-per-day-overwrite.** Discussed since it's real DOMS-timing signal, not just data clutter — the fix above makes "most recent entry" reliably mean the truly latest one, which is all the compass/preview need (they want "how sore right now," not an intra-day time series). No need to average or retain every same-day point for that purpose; the Days tab (above) already lets old same-day entries be corrected individually if needed.

### Soreness decay — implemented 2026-07-22
The user's own framing: soreness should be loggable twice a day (AM/PM), carrying forward if only one is logged, and should **naturally fade** the longer it goes unconfirmed — someone who logged a "4" then didn't touch that region (or the app) for a week is very unlikely to still be a real "4" in life, but the readiness engine had been treating that stale log as fully current forever.

**Turned out the twice-a-day/carry-forward part was already correct, free of charge** — no code change needed. Soreness is stored per-day in `metrics_log`; `MetricsRepository.getLatest`'s `date DESC, logged_at DESC` ordering already means the most recent same-day entry wins if both AM and PM are logged, and a single log for the day just naturally carries through the rest of that day untouched if only one gets entered. The one real gap was the multi-day case: `getLatest` had no time bound at all, so a log from arbitrarily far in the past was read as still 100% current — this is what actually needed fixing.

**Fixed with `MetricsRepository.effectiveSorenessLevel(region)`** — looks up the most recent log for a region, then decays it toward 0 based on days elapsed since it was logged (0 days = untouched, full value). Rate: **`sorenessDecayPerDay = 1/1.5`** (~1 level every 1.5 days, so a max "5" fully resolves to 0 in about 7.5 days). Landed on this after a literature check (DOMS research consistently puts peak soreness at 24-72h post-exercise with resolution typically complete within about a week, most commonly cited as 3-7 days) — the user's own initial guess of "1 level per 2 days" would take a full 10 days to resolve a max rating, a bit slower than typical. Wired into `ReadinessEngine.computeMuscleReadiness`'s soreness factor (previously a raw `getLatest().value.round()`), which is the only current consumer that needed to change — `computeCategoryStatus` never factored in soreness at all.

**Explicitly flagged as a rough starting rate, not a precise formula, per the user's own concern:** soreness is entirely self-reported on a 0-5 scale, and what a "5" *means* is inherently personal — the user's own example, someone who trains hard might call a "5" "severely overtrained, can't use the limb, takes a week," while someone else's "5" is "very sore, three days." A single flat rate can't capture that gap. **Earmarked as a real future direction, deliberately not built yet**: learn each user's own actual gap-then-relog pattern (how much a region's self-reported soreness tends to have actually dropped after N days without training it) rather than assuming everyone decays the same way — possibly varying by muscle group too, not just by person. Deferred because a new user has no history yet to learn a personal rate from; revisit once there's enough real usage to learn from. `decayedSorenessLevel` (the pure decay formula) is unit-tested in isolation (`test/data/metrics_repository_decay_test.dart`) for exactly this reason — easy to swap in a smarter model later without re-deriving the surrounding wiring.

**Both deferred gaps closed in a follow-up round (2026-07-22):**

### Soreness AM/PM slots and the two deferred display gaps — implemented
Closes both items the round above deliberately left open, plus adds the actual feature the decay math had been assuming existed: explicit, editable AM/PM slots.

**Schema:** `metrics_log` gained a nullable `time_slot` TEXT column (migration v21, `DatabaseHelper._migrate` case 21) — `'AM'`/`'PM'`, null for steps/sleep and for any soreness entry logged before this shipped. `MetricEntry.timeSlot` (`SorenessTimeSlot? enum`) wires it through `toMap`/`fromMap`. `BackupService` needed no changes — its `PRAGMA table_info`-driven export/import already picks up new columns automatically.

**Why this was a real gap, not just the decay work:** logging twice a day already *worked* (previous section), but there was no way to say "this log is the AM one" vs "the PM one" — so there was no way to go back and *correct* a specific past entry without just appending a confusing duplicate. `SorenessBodyMapForm` now has an AM/PM toggle (`_TimeSlotToggle`, same pill-switch visual pattern as `_UnitToggle` in Settings) sitting directly above the Save button alongside the date picker (moved down from the top, per the user's explicit ask — "what am I about to save, and for when" reads as the final confirmation before committing, not upfront setup). Picking a date + slot loads exactly what's logged there via the new `MetricsRepository.getByTypeDateAndSlot`; Save now calls `upsertSorenessEntry` (delete-then-insert on the exact `(metric_type, date, time_slot)` triple) instead of a plain `insert` — this is what actually makes "override a wrong past log" possible. Default slot: time-of-day when logging fresh (before noon → AM), always AM when opening to edit a past day (simplest predictable choice, one tap to check PM).

**Ordering fix that came along with it:** `MetricsRepository.getByType`'s `orderBy` gained `time_slot DESC` ahead of `logged_at DESC` (`'PM' > 'AM'` lexicographically; `NULL` sorts last in `DESC`, so legacy unslotted rows fall behind explicit ones for the same date). Needed once slots became explicit and correctable — backfilling/fixing an AM entry *after* a PM one was already logged shouldn't make the AM entry look "more recent" just because it happened to be saved later in real time; slot now outranks raw save-time.

**Gap 1 closed — Overview soreness card now shows the current (decayed) picture, not just raw logs.** `MetricsScreen._load()`'s soreness map now calls `AppServices.metrics.effectiveSorenessLevel(region)` (the same function the readiness engine uses) instead of a raw `getLatest().value.round()` — `_latestSoreness` is `Map<SorenessRegion, double>` now, matching the readiness engine's own type, so the Overview card and the heatmap/status icons can no longer silently disagree about the same region.

**Gap 2 closed — Days tab shows only what was actually logged, per-slot, tagged.** Previously collapsed a day's soreness into region *names only* (a `Set<String>`, dropping the value entirely). The Days tab intentionally still shows zero decay/carry-forward — that's what the Overview card is for now; Days is "what did I actually report, as reported."

### Bug fixed — AM and PM need to be separate rows, not tags mixed into one (2026-07-22)
First pass at Gap 2 put both an AM and a PM entry's tags into the *same* Days-tab row (`'Quads (3) · AM'`, `'Quads (2) · PM'` both inside one row's tag list). Real problem the user hit: that row's single `onEdit` action could only open one slot's map (defaulted to AM), so there was no way to tap into "edit the PM one specifically" — editing always landed on AM regardless of which entry the user meant, which produced confusing-looking results (e.g. tapping to fix a PM value while looking at the AM map, or vice versa) that read like the app was merging values together. It wasn't actually merging anything — `MetricsRepository.upsertSorenessEntry` was already correctly replacing by exact `(metric_type, date, time_slot)` — the confusion was entirely from opening the wrong slot's map by default.

**Fixed by grouping per `(date, slot)` instead of just per date** — `MetricsScreen._sorenessGroupedBySlot()` (a new shared helper, backed by a small `_SorenessGroup` holder) is now used by both the Days tab and the Overview history popup (`_sorenessHistoryRows`), so an AM log and a PM log on the same date are two separate rows: `'Soreness (AM)'` and `'Soreness (PM)'` as the row label (Days tab) or the slot shown via `valueText` (history popup, which has no separate label field). Each row's tags now go back to plain `'Quads (3)'` (no slot suffix needed on the tag itself — the row it's in already says which slot). `SorenessBodyMapForm` gained an `initialSlot` parameter so `_editSorenessDay(date, slot)` can pin the form to the exact entry a given row represents, instead of always falling back to its own AM default. **Legacy entries logged before AM/PM existed** used to just sit unslotted with no path to being reloaded for editing — closed by the migration below, which backfills every real pre-existing entry with a slot rather than leaving this as a permanent limitation.

### Migration to backfill AM/PM onto real users' existing soreness history (v22)
The gap above ("legacy null-slot entries can't be reloaded into the edit form") was originally accepted as a permanent limitation — but it isn't really acceptable for people who already have real logged history from before this feature existed (the app has active Play Store internal testers). `DatabaseHelper._migrate` case 22 backfills `time_slot` onto every pre-existing soreness row, grouped by `(date, metric_type)`:
- **One entry that day** → `AM` (the common case — most people only logged once a day).
- **Two or more** → earliest-logged → `AM`, latest-logged → `PM` — matches what `MetricsRepository.getLatest` was already treating as "today's real value" before AM/PM existed, so the backfilled PM slot lines up with whatever the app was already showing as current.
- **More than two** (a rare same-day double-correction from before upserts existed) → keeps the earliest and latest, **deletes** anything strictly in between — safe because only the latest entry per day was ever actually read by any code path before this feature shipped, so those middle rows were already-dead data, not information anyone was relying on.

Runs once, automatically, the next time an existing install upgrades past v21 — no user action needed, and nothing about their historical soreness numbers changes, only which slot each one now belongs to. Fresh installs never see this (nothing to backfill, `time_slot` starts populated correctly from the first real log).

### Demo data updated to actually exercise the AM/PM UI (2026-07-22)
`TestDataService._writeSoreness` was writing every synthetic soreness entry with `timeSlot: null` (unslotted, same as any pre-migration real entry) — meaning loading fresh demo data would never show the new per-slot rows or let anyone test editing a specific slot. Now assigns a random AM or PM to each synthetic entry, and writes via `upsertSorenessEntry` (the canonical write path) instead of a plain `insert`, for consistency with how the real form saves.

### Soreness sub-splitting — implemented
The original 5 broad categories (core/back/arms/legs/chest) lumped together muscles that genuinely different lift patterns train — e.g. "Back" mixed pulldown/pull-up soreness (lats, upper back) with deadlift/good-morning soreness (erectors, lower back). Went finer, but **by common lift-pattern grouping, not full 23-`Muscle` anatomy** — the user's explicit concern was tap-precision/decision fatigue causing fall-off at full granularity, so this stops well short of that. New `SorenessRegion` enum (`14` regions, `metric_entry.dart`), each mapped to specific `Muscle` values via `MuscleMap.sorenessRegionGroups` (a parallel, finer sibling to `MuscleMap.broadGroups` — that one is untouched, still used for Training Composition and the Home status icons' recovery-window math):
- **Chest** — unchanged, still one region.
- **Core** → Abs / Obliques (straight-plank/crunch soreness vs. side-plank/twist soreness fire differently).
- **Back** → Upper Back / Lower Back.
- **Arms** → Biceps / Triceps / Shoulders / Forearms.
- **Legs** → Quads / Hamstrings / Glutes / Calves / Inner Thigh.
- Minor joint-adjacent regions (knees, tibialis, ankles, feet) fold into the nearest major region (quads/calves) rather than getting their own tap target.

Because the tap interaction is "tap wherever it's sore on the body silhouette" (not a checklist you fill out every field), more categories doesn't mean more *required* taps per log — the existing fine-grained `Muscle` tap targets in `flutter_body_heatmap` already supported this resolution, the app was just coarsely bucketing them. `SorenessBodyMapForm` now routes a tap to its `SorenessRegion` (via `MuscleMap.regionForMuscle`) instead of the old broad `ExerciseCategory`; `ReadinessEngine.computeMuscleReadiness`'s soreness-proxy step reads per-region too, so e.g. sore hamstrings no longer dampen quad readiness.

**Migration note (real data existed by the time this shipped):** old `MetricType.fromKey` has no fallback for an unrecognized key, so leftover rows under the retired 5 broad soreness keys would have crashed anything reading `metrics_log` broadly (the Days tab, notably) the next time it ran. Version-7 migration remaps old rows to one representative sub-region per old category (`soreness_core`→Abs, `soreness_back`→Upper Back, `soreness_arms`→Biceps, `soreness_legs`→Quads, `soreness_chest` unchanged) — not anatomically precise for that older history, but preserves it instead of crashing or silently dropping it. `TestDataService`'s synthetic soreness generator uses the same representative-region mapping.
- **Weight (weekly avg)** — `LabeledTrendChart`, prediction extension on, numeric axis ticks, but each plotted dot is **that week's average**, never a raw daily bodyweight reading. This is the resolved compromise from the original "don't be weight-motivated" ask — see `00_UX_DESIGN.md`.
  - **Daily-log opt-in (2026-07-27) — a deliberate, disclosed exception to the rule above, not a reversal of it.** The Weight card's settings gear gained a "weekly average / daily log" toggle (`MetricLayoutItem.dailyView`, `MetricChartPoints.dailyBodyweight` — plain per-date points, same shape as every other metric's, sorted, no averaging) — user's own explicit request. **Defaults off** (weekly average, unchanged prior behavior for anyone who hasn't touched it) and only reachable through the same edit-mode gear every other per-card setting already lives behind, not a casual toggle sitting in the open. The trend curve's 42-day trailing window (`00_UX_DESIGN.md` "Trend line math") is genuinely time-based, not point-count-based, so denser daily input doesn't change its math, only its density. The separate "hide my weight" number-masking setting (`06_SCREEN_settings.md`) is untouched and still applies either way — this toggle is about point *density*, not whether the number itself is masked.
- **Cycle** — deliberately nondescript per `00_UX_DESIGN.md`: plain "Cycle" label + calendar icon + a plain count ("N days logged"), same visual weight as other cards, no preview chart. Tap opens `CycleDetailScreen`. **Demo data is gender-gated (2026-07-17)** — `TestDataService` only generates synthetic cycle data when `UserProfile.gender == Gender.female`; generating it regardless of the current gender setting would just be irrelevant noise on a male-set demo profile. **The card itself is gender-gated too (2026-07-20)** — hidden from the Overview tab entirely when the profile is set to male, not just left with no demo data. Nothing is deleted: any cycle entries already logged (from trying the female setting) stay in the database untouched and the card reappears exactly as it was if the setting is switched back. Settings' About text and the `cycle` overlay option below both respect the same check.

## Overview tab editing (2026-07-20, reworked 2026-07-25)
Same "edit mode" idea as Home (`02_SCREEN_home.md`), applied here after the two screens drifted out of parity. A pencil/check icon in the AppBar (Overview tab only, hidden on Days) toggles edit mode:
- **Reorder** — drag handle on each card, `MetricLayoutSettings.order` persists the sequence (`AppServices.setMetricWidgetOrder`, same generic string-settings row pattern `HomeLayoutSettings` uses).
- **Reconciliation** (`_currentMetricOrder`) — the persisted order is checked against current reality on every build: a `cycle` entry is dropped if the profile isn't female anymore (even if it was in a customized order saved while female), a `customMetric` entry whose metric was actually deleted (not just hidden) is dropped, and any custom metric created since the order was last saved gets appended automatically so a brand-new metric never silently fails to appear.
- `MetricWidgetId` enum (`steps`/`sleep`/`workoutDuration`/`soreness`/`weight`/`cycle`/`progressPhotos`/`customMetric`) plus `MetricLayoutItem` (type + optional `customMetricId` for the repeatable `customMetric` case) live in `lib/services/metric_layout_settings.dart`, deliberately mirroring `HomeLayoutSettings`'s shape rather than inventing a new one.

### Edit-mode controls reworked (2026-07-25) — column layout, hide-in-place, per-card settings gear
Three changes, made together after the original row layout and hide/re-add popup started feeling cramped and indirect once cards could also carry settings (goals, time frame — see below).

**Controls moved from a row to a column.** The original layout put the eye-off icon and the drag handle side by side, both eating into the card's own width and visibly squishing every plot in edit mode. Now it's `Row(Expanded(card), Column(drag, eye, gear?))` — drag on top, then show/hide, then the settings gear if this card type has any settings — so the controls only ever cost one icon's width next to the card, not two or three. Same `TapIcon` sizing throughout (`00_UX_DESIGN.md` "Tap targets"), just stacked instead of spread.

**Hiding is now in-place, not a remove-then-repopup.** `MetricLayoutItem` gained a `hidden` bool (plus `stableKey`, a `type:customMetricId`-only identity used for the `ReorderableListView`'s `ValueKey` — `token`, the persisted string, now changes whenever any of `hidden`/`monthsOverride`/`showGoal` is toggled, which would otherwise make the list think an in-place settings change was a totally different item mid-interaction). Tapping the eye toggles `hidden` on that exact item without removing it from the order — it stays reorderable, and in edit mode renders **fully, at full size, just dimmed** (`Opacity(0.4)`) rather than collapsing to a bare icon-and-name row, so what's being toggled is never in question. Outside edit mode a hidden card simply doesn't render. **The separate "show a hidden card" popup in the AppBar is gone entirely** — with hiding now reversible in place, there was nothing left for it to do; the only way to add a genuinely new card is a new custom metric (`+` in the AppBar), same as it already was for that path.

### Per-card settings gear (2026-07-25)
A `Icons.settings_outlined` gear appears in the column above only for a card type with `MetricWidgetId.hasTimeFrame == true` (every type with a `LabeledTrendChart`: steps/sleep/weight/workoutDuration/customMetric) — `soreness`/`cycle`/`progressPhotos` have nothing to configure, so they get no gear at all rather than an empty popup. Opens `MetricCardSettingsSheet` (`lib/screens/metrics/metric_card_settings_sheet.dart`):

- **Time frame** — a dropdown of fixed, sensible choices (1/3/6/12 months, "All time," or "Default"), backing `MetricLayoutItem.monthsOverride`. **"Default" tracks `HomeTrendSettings.months` live**, not a value copied at save time — the user's own explicit call: a card left on Default should keep following the shared Home setting even if that setting changes later, only a card explicitly switched to a specific month count becomes independent of it. This is also what retired the old flat ~6-month (`_dashboardHistoryDays = 183`) cutoff this screen used before every card could have its own window — cutoffs are now computed the same real-month-subtraction way Home's trend cards already do (`_cutoffFor`), not a day-count approximation. "All time" is represented as a cutoff of `DateTime(1970)` rather than a separate nullable "no cutoff" code path through `MetricChartPoints` — simpler, and functionally identical since no real data predates that.
- **Goal line toggle** — shown only if the underlying metric actually has a goal value set (steps always does; weight/sleep only if set in Settings; a custom metric only if `kind == number` and its own goal is set — see "Goals" above). Same `Icons.flag`/`Icons.outlined_flag` two-state convention as Home's `MetricTrendEditSheet`. Backs `MetricLayoutItem.showGoal`, which now also feeds every relevant `LabeledTrendChart` on this screen (steps/sleep/weight/customMetric) — previously only Home's Metric Trend cards actually drew the goal line; the Metrics screen's own matching cards never did until now.

**Not carried over to Home yet** — the user asked to do Metrics first since it's the more involved case, then bring over whatever makes sense to Home's own edit mode in a follow-up round. `HomeLayoutItem` doesn't have `hidden`/a settings gear as of this round; Home's existing per-card pencil (Strength/Metric Trend, This Week) is untouched.
- **Progress Photos** (implemented 2026-07-17) — a date-stamped image log, shown as `ProgressPhotoTimeline` (`widgets/progress_photo_timeline.dart`) on the Metrics card: a plain horizontal line with a dot per day that has at least one photo, dot size growing with that day's photo count. No y-axis/value — there's nothing to plot besides presence over time, unlike every other card here. A camera icon on the card opens the add flow directly (date field, defaulting to today but backdatable, then Camera/Library) without leaving Metrics. Files are copied into the app's own document storage (`ProgressPhotoRepository.storePickedFile`) rather than trusting whatever transient path the picker hands back, and deleting a log row also deletes its backing file. `image_picker` is a new dependency; Android gained the `CAMERA` permission (manifest) for the capture path.
  - **Reworked into a 3-screen flow (2026-07-17), same day as it first shipped.** Tapping the Metrics card now opens `ProgressPhotoAlbumScreen` — a "quick view" grid, one **stack per day** (`_PhotoPileTile`): every photo for that day pinned to the same bottom-left corner (`Transform.rotate` pivoting on `Alignment.bottomLeft`) and rotated a little more per photo, so a multi-photo day reads as a pile of prints tossed down, not a flat thumbnail. Tapping a stack opens `PhotoSwipeScreen` scoped to just that day (every photo, not capped); a carousel icon in the album's AppBar jumps straight to `PhotoSwipeScreen` over **every** photo, newest first — the original all-photos swipe view this feature launched with, now one tap away instead of the default.   - **Pile preview capped at 3, always the most recent (fixed 2026-07-17, day of).** First version capped at 4 and just took whichever photos happened to sort first — for a day with more than the cap, that silently showed the *oldest* ones and dropped the most recent, which read as "not in date order." Now caps at 3 and, when a day has more, keeps the most recent 3 (sorted by `taken_at` ascending, then the last 3 taken) — painting last-in-list-on-top means the newest photo ends up visually on top of the pile too. `PhotoSwipeScreen`'s photo lists are also now explicitly re-sorted newest-first at the call site (`_newestFirst`) rather than trusting upstream order, so swiping is reliably chronological regardless of how the list was assembled.

- **Custom metrics / the "metric builder"** (implemented 2026-07-17) — an unlimited set of user-defined metrics, each rendered as its own card (name, a notebook icon to browse/correct past entries, a `+` icon to log a new value, a trash icon to delete the whole metric — deletion cascades its entries with no confirmation-heavy dialog, since a mis-built metric carries none of the weight a real exercise's logged sessions do). A `+` in the Metrics AppBar opens `CustomMetricBuilderSheet`: name it, then pick a `kind` (`CustomMetric`/`custom_metrics` table):

  - **Scale** — a 0-5 level, same shape as muscle soreness, with a choice of icon (`ScaleLevelPicker`, a generalized `FlameLevelPicker`): flame, star, dot, plus **heart, bolt, moon, drop** (added 2026-07-17, same day the picker shipped) — deliberately multi-use (heart for heart rate *or* general mood/how-good-it-felt, bolt for energy, moon for sleep quality, drop for hydration) rather than one icon per specific tracked thing. Thumbs-up was considered and dropped — didn't read clearly at this icon size/style.

  - **Log/history view (implemented 2026-07-17)** — `CustomMetricHistorySheet`, opened via the card's notebook icon: every logged entry for that metric, newest first, with its date/formatted value and a delete action.   Logging a value (`CustomMetricEntrySheet`) shows whichever input matches the kind (number field / `ScaleLevelPicker` / class chips) plus a backdatable date field. ## Goals (implemented 2026-07-24)
Extends the existing Steps-goal concept (an `int`, always set, defaulting to 10,000, adjustable in Settings, driving Home's steps ring — `06_SCREEN_settings.md`) to weight, sleep, and numeric custom metrics — same idea, but genuinely optional. See `02_SCREEN_home.md` "Goals" for how these actually surface on Home (the dashed chart line, the This Week ring picker); this section covers where the goal values themselves live and how they're set.

**Storage:**
- `UserProfile.weightGoalLb`/`sleepGoalHours` — nullable `double`s (unlike `stepsGoal`, "no goal set" is the common starting state here, not an edge case to work around). Persisted as two new `app_settings` keys (`weight_goal_lb`, `sleep_goal_hours`); `AppServices.setWeightGoal`/`setSleepGoal` delete the key entirely on `null` rather than writing a placeholder, so a cleared Settings field genuinely goes back to unset.
- `custom_metrics.goal REAL`, nullable — migration v23 (`DatabaseHelper._migrate` case 23), mirroring exactly how `allow_multiple_per_day` was added in an earlier version (`ALTER TABLE`, no backfill). `CustomMetric.goal`, wired through `toMap`/`fromMap`.
- `CustomMetricRepository.updateDefinition` — new method; this app had no way to edit an existing custom metric's definition at all before this (only create + delete).

**Settings** — two more rows in the existing "Goals" card, right under Steps goal, same `TextField` + `onSubmitted`/`onTapOutside` auto-save pattern already used there and for Birth year, but decimal-capable, and **empty is a legitimate, intentional state** here (clearing the field and blurring/submitting sets the goal to `null`, no error) — unlike Steps, which still rejects empty/invalid outright since a stepless goal was never a state that concept was built to represent. The Weight field displays/accepts the current display unit (`Units.displayValue`/`Units.toLb`, the same conversion every other weight display in this app goes through) while storing canonically in lb underneath.

**Custom metric goals apply to `kind == number` only** — not `scale` (already bounded 0-`scaleMax` with its own gauge widget) or `classes` (categorical, no numeric goal makes sense). `CustomMetricBuilderSheet` gained an optional "Goal" field, shown only for that kind, set at creation. For an already-created metric: rather than build a general metric-definition editor (a bigger feature this app doesn't have and wasn't asked for), a small dedicated flag/outlined-flag icon appears next to number-kind metrics in the Metrics screen's custom-metric card, opening a single-field dialog (blank clears it) that calls `updateDefinition` — the one thing about an existing metric that's safe to change anytime, since unlike `kind`/`scaleMax`/`classLabels`, a goal never changes what past logged entries *mean*.
