# Screen: Lifts

List + detail for every tracked exercise (seeded big lifts + graduated custom movements), plus a Workouts tab for browsing what was logged by day.

## Tabs
Two tabs at the top of this screen: **Lifts** (default) and **Workouts**.

### Lifts tab — implemented
- One card per exercise: name, **category pills** (multi-tag — an exercise can carry more than one of legs/core/arms/back/chest/push/pull, rendered as small rounded pill chips; e.g. Bench = chest+push+arms, Back Squat = legs+push, Deadlift = back+legs+pull), **equipment/type pills** (a separate tag dimension — `ExerciseType`: cardio/machine/compound/bodyweight, rendered muted/outlined to read as distinct from the muscle-group pills; added after real gym use surfaced a need to tag non-barbell movements for findability), and a **5-bar signal-style readiness indicator** on the right side near the chevron.
  - Equipment tags are purely descriptive except `bodyweight`, which also switches the e1RM/Predicted-Next/Goal-gauge calculations to a rep-based model — see `07_SMART_TRENDS.md` "Bodyweight movements."
  - **Revised:** this readiness score now reads from the same compass as Home's "Primed for Growth" map — `ReadinessEngine.readinessForExercise` averages the per-muscle readiness across whatever muscles this exercise hits (`MuscleMap.musclesFor`), then `ReadinessEngine.toBars` maps that 0-1 score onto the existing 0-5 bar scale. No second readiness formula anymore; this was previously pure recency (`TrendEngine.readinessScore`), now fully superseded. See `07_SMART_TRENDS.md`.
- **"+ Add custom movement" — a 3-step wizard (2026-07-16, was a single page).** Step 1: name + category/equipment pills + optional YouTube URL (all optional now except name — categories used to be required, no longer are, per the user's "everything skippable except name and muscles" call; **no movement-pattern pills** — see below). Step 2: **muscle selection** (see below) — the only other required field. Step 3: an optional custom goal value and optional notes. A small dot-row shows progress; Back/Next buttons, the last step's button reads "Save." Skipping just means leaving a field blank, not a separate skip action. **Editing an existing exercise stays a single page** (`AddExerciseSheet` with `existing` set) — a quick tweak shouldn't force a multi-step flow — but gained the same "Select Muscles" button as the wizard, and categories are no longer required to save there either.
- **Delete Exercise** (edit mode only, in the same Add/Edit sheet): confirm dialog states how many logged sessions will also be deleted (the `exercises` → `lift_sessions` foreign key cascades), since this is genuinely destructive. If deleted from within Lift detail's edit button, that screen pops itself afterward since the exercise it was showing no longer exists. Plain confirm dialog for now — the user wants a friskier randomized-math confirmation for this and other destructive actions (wipe/load test data in Settings too) as a deliberate follow-up, not built yet.
- **Muscle selection — implemented 2026-07-16** (previously deferred): a custom exercise's fine-grained muscles are now settable via `MuscleSelectorSheet` — see "Add/edit exercise — muscle selection" below. All 93 **seeded** exercises still carry hand-curated defaults (`MuscleMap.liftMuscles`, `00_UX_DESIGN.md` "Lift muscle-highlight diagram") as a fallback for anyone who hasn't set their own.
- **Bulk exercise library (implemented)** — 93 seeded exercises total now, spanning compound barbell/dumbbell lifts (including Olympic-style jerks/snatch), isolation accessories, bodyweight movements, named machines/cables, and one cardio entry. See `01_DATA_MODEL.md` for the full breakdown and `07_SMART_TRENDS.md`/`test_data_service.dart` for how the demo-data generator handles this (rotates a curated ~11-lift routine subset, not the full library, so trend charts still have enough points to look like something).
- **v11 round (implemented)** — two additions after real gym use: (1) 8 more **dynamic bodyweight core exercises** — Russian Twist, Dead Bug, Bicycle Crunch, Flutter Kicks, V-Up, Leg Raise, Bird Dog, Superman — filling a real gap (only Sit Up/Crunch/Hanging Leg Raise existed before). Isometric holds (planks, side planks, hollow holds) were deliberately excluded — this app's data model is reps/weight/RPE-shaped, and "how long did you hold it" doesn't fit that without a real design pass, not just a data-entry one; revisit if it turns out to matter. (2) 8 **machines cross-checked against the user's actual gym equipment** — their unbranded machines turned out to match Precor's Resolute (selectorized) and Discovery (plate-loaded) lineups closely enough to use as a reference list: Ab Crunch Machine, Back Extension Machine, Rotary Torso Machine, Glute Extension Machine, Bicep Curl Machine, Triceps Extension Machine, Seated Dip Machine, Low Row Machine. Near-duplicate machine variants of movements already well covered (e.g. Precor's Incline Press/Decline Chest Press/Seated Row/V-Squat machines) were deliberately skipped rather than added 1:1 — the app tracks by movement pattern for readiness/pattern-completeness purposes, not by exact machine brand/model, and several existing entries (free-weight + cable + machine variants) already satisfy those same patterns. Cardio equipment (bikes, treadmills, ellipticals) was also deliberately not expanded — Rowing Machine's "reps = meters" is already a stretch of the rep/weight/RPE model, and duration/distance-based cardio tracking is a real design decision, not something to bolt on via more seed rows.

### Filter and Sort — implemented
Two buttons at the top of the Lifts tab, below the tab bar (`_FilterSheet` / `_SortSheet`, both bottom sheets) — supersedes the earlier "shelved until the list grows" call, prompted by real gym use once the custom-exercise list actually started growing.
- **Filter** — a multi-select of every category/equipment pill, grouped into three sections in this order: **Muscle group** (legs/back/chest/core/arms), **Push/Pull**, **Type** (`ExerciseType`: cardio/machine/compound/bodyweight/isolation). Matching is **OR across every selected pill, regardless of group** — tapping only "Chest" shows anything tagged chest (e.g. Bench Press); tapping "Chest" + "Machine" shows anything tagged either. No filters selected shows everything. The active set lives in `_LiftsScreenState._activeFilters` (a `Set<Object>` mixing `ExerciseCategory`/`ExerciseType` values, checked against `Exercise.categories`/`Exercise.equipmentTags` respectively) and is passed by reference into the sheet so toggling a chip updates the list live.
- **Pinned-only quick toggle** (implemented) — a standalone push-pin `IconButton` next to Filter/Sort (not inside the Filter sheet, since it's used often enough to deserve one tap instead of two). Filters `_visibleExercises` down to `Exercise.pinned` before category filters apply. See "Pinned lifts" below.
- **Sort** — single-select from **Alphabetical**, **Most used**, **Push/Pull**, **Muscle group**, **Type**, **Readiness** (the first two added this round, once the library grew to ~75 exercises and "what do I actually use" became a real question). Alphabetical just ties-breaks on name (matches the DB's default order, but now selectable/visible as an explicit choice rather than only being the implicit no-sort state). Most used ranks by total logged-session count per exercise (from the already-loaded `_allSessions`, most sessions first) — the direct answer to "I hit Back Squat a lot but barely touch Front Squat, put Back Squat on top." The remaining four sort by a fixed priority order over an exercise's tags (e.g. muscle group priority is legs → back → chest → core → arms; an exercise sorts by the earliest tag it carries, ties broken alphabetically by name); Readiness sorts by the same `ReadinessEngine.readinessForExercise` score already used for the list's bars, most-ready first. No sort selected keeps the default alphabetical-by-name order from the DB query.
- Pinned filter, category filter, and sort compose (pinned → category filter → sort) via a single `_visibleExercises` getter.
- **Search — implemented.** A magnifying-glass `IconButton` at the end of the Filter/Sort/Pin row expands into a full-width text field (with a close `×` to collapse it back) in place of that row — matches the user's "widens to show the input" ask, via a simple expanded/collapsed toggle rather than an animated width transition. Matching is substring, case-insensitive, on exercise name, and is applied **last** in `_visibleExercises` (after pinned/category filters) — so it narrows whatever's already visible rather than searching the whole library, e.g. a "Legs" filter + typing "bench" correctly shows nothing rather than falling back to the full list.

### Pinned lifts — implemented
A `pinned` bool column on `exercises` (push-pin icon, `04_SCREEN_quick_log.md`-adjacent but toggled from Lift detail's own AppBar) — added once the seeded library hit ~75 exercises and "I only need maybe 15 regularly" became the real problem to solve, not just findability.
- **Toggle**: a push-pin `IconButton` on Lift detail's AppBar, leftmost of the three action icons (pin, then `+` log-set, then edit pencil) — `_LiftDetailScreenState._togglePinned`, filled `push_pin` (accent-colored) when on, outlined when off.
- **Drives the quick-log picker's default list**: `LogLiftForm`'s exercise picker (opened from the FAB) defaults to showing **only pinned exercises**, not all ~75 — anything off the beaten path is either one tap away from its own detail page, or reachable by typing a search term. Always includes the `preselected` exercise even if unpinned. **2026-07-15: became a searchable picker** (`ExercisePickerField`, see "Searchable exercise picker" in `07_SMART_TRENDS.md`) rather than a pinned-only dropdown — typing searches the full library by name, so an unpinned lift no longer needs a detour through the Lifts tab to log against.
- **Defaults**: the original 7 seeded lifts (5 barbell + Pull Up/Push Up) are pinned by default — both for fresh installs (`_seedExercises`' `'pinned': true` entries) and backfilled onto existing installs via the version-6 migration, so the new pinned-only dropdown isn't empty for anyone upgrading. The ~68 bulk-added exercises start unpinned.
- **Visible elsewhere**: a small pin icon next to the exercise name on each Lifts-list card when pinned, and pinned exercises sort first (then alphabetical) in the Home Strength Trends picker (`02_SCREEN_home.md`).

### Workouts tab — implemented
Added so the user can find a specific logged lift without knowing which exercise it was under — groups every logged session (across all exercises) by date, most recent day first. Each row: a left-edge vertical color bar, the exercise name, a brief summary (set count + top weight, unit-aware), a pencil icon opening the same edit sheet as the Lift detail history (see below), and **tapping the row itself opens that exercise's `LiftDetailScreen`** (same destination as tapping it from the Lifts tab) — session lookups resolve the exercise name via the already-loaded exercise list, no extra query per row.

- **Intensity bar color — revised.** The left-edge bar's color is `lerp(border, accent, session.avgRpe / 10)` — i.e. this session's **average** logged RPE (`SessionWithSets.avgRpe`, sets without an RPE excluded rather than counted as 0) directly against the fixed 1-10 RPE scale. Originally this was a **sum** of RPE across the session's sets, shown relative to the single hardest session in the user's *entire history* — on review that was the "off" feeling reported: a session's color depended on its set count (more sets always outscored fewer-but-harder ones) and drifted every time a new all-time-hardest session got logged, plus any set logged without an RPE dragged the sum down as if it were an easy set. Average-against-a-fixed-scale fixes both — a 3-set RPE-9 session now reads redder than an 8-set RPE-5 session, and the color is stable across app use rather than shifting under you.
- Within each date group, sessions tied to a Workout Planner `PlannedSession` are further nested under a day-label sub-header with its own edit icon (opens `ActiveDayScreen` in view/edit mode) — see designFiles/10_WORKOUT_PLANNER.md "Workouts-tab annotation" for the full shape, including the group's visual styling (accent-tinted background + left border) and tap-to-open-workout behavior.

## Lift detail — reorganized this round
Reordered specifically to fix "front-loaded clutter" — features had been added incrementally with no deliberate layout pass. Current order, top to bottom:

1. **Log-set (+) and Edit buttons** (AppBar) — the `+` opens `LogLiftForm` pre-scoped to this exercise (skips the exercise dropdown), added after real gym use made "navigate back to the FAB and re-pick the exercise" feel like unnecessary friction mid-workout. Edit pencil is the same Add/Edit/Delete sheet as the Lifts list, updates in place.
2. **Compact stat row** (3 equal-width cards, tightened padding — `AppCard` now takes an optional `padding` override since these are mostly 1-2 lines of text and don't need the standard card padding): **Last trained**, **Last intensity** (label shortened to a single word — "Light" instead of "Recovery / light" — after the two-word version wrapped awkwardly at this width), **Readiness** with an "i" info icon (same `readiness` glossary entry as Home's muscle map) shown via `ReadinessSegmentedBar` — a new horizontal 5-segment bar, not the Lifts list's vertical `ReadinessBars`, since a compact card has no vertical room to spare and the vertical dimension of the wifi-style bars didn't carry any information here. Same compass-derived score either way (`ReadinessEngine`), just two different visual treatments for two different amounts of space.
3. **Predicted-next-e1RM card** (also tightened padding): the redesigned `RangeIndicator` (see below) — always visible, no tap-to-expand, per `00_UX_DESIGN.md` Confidence indicators.
4. **Muscles Worked (left half) + Notes (right half)**, side by side in one row (`IntrinsicHeight` so both sides match height): the front+back muscle heatmap shrunk to half its old width to make room for the user's own free-text notes (**2026-07-16: replaced the curated "Overview" cues entirely** — see below) plus the "Watch form video" YouTube button, moved here from its old standalone spot. No embedded video player yet — deliberately deferred, see below.
5. **Heavy Set History** (renamed from "e1RM Trend", 2026-07-15): `CenteredTrendChart`, full history (no 6-month cap, unlike the dashboards), prediction extension on. Plots each session's literal heaviest-set weight (no formula), dot size encoding the rep count on that set — see `07_SMART_TRENDS.md` Layer 2.
6. **Goal** (implemented) — the long-arc target, see below: either a bodyweight-ratio strength standard or the user's own custom goal. For barbell lifts with a standard, shown when a bodyweight entry exists and the exercise has one (the 4 lifts with real published-style figures, plus Front Squat derived from Back Squat). For `bodyweight`-tagged lifts (Pull Up, Push Up), a rep-count standard is used instead, needing at least one plain-bodyweight set logged (no bodyweight entry needed for this path). A custom goal (2026-07-15, see below) can substitute for either, or coexist with a toggle to switch between them. Nothing shown only when neither a standard nor a custom goal applies.
7. **(Open slot)** for additional charts — the user floated a box-plot-style "range of weights per workout, warm-up to heaviest" idea, not committed to yet.
8. **History**: full session/set log, each showing a pencil icon to edit or delete that specific session, reps, weight (unit-aware), RPE, and session notes when present.

### Goal: bodyweight-ratio strength standard, or a custom target (implemented)
Deliberately a **separate, longer-arc target** from the "Next Heavy Set" box above — that one is "try for this next" (near-term, projected from recent sessions at a characteristic rep count); this one is "here's what a realistic long-term target looks like for this lift." Not shown in the same box on purpose so the two different time horizons don't get conflated.

- **`StrengthGoalGauge`** (published standard): a horizontal progress bar with 5 tick marks at the Beginner/Novice/Intermediate/Advanced/Elite thresholds (`StrengthStandards`/`BodyweightRepStandards`, `07_SMART_TRENDS.md`) — each tick labeled with its target above and the tier abbreviation below. For weighted lifts, the fill/position and the "True max: [value], [reps] reps" line below it are the **literal heaviest weight ever logged, plus the rep count it was hit at** (added 2026-07-15) — never Epley-projected and never decayed. A separate "Predicted 1RM: [value]" line (with its own "i" tooltip) shows a most-recent-history e1RM estimate instead, so an estimate never gets mistaken for something actually lifted — **no decay on this either** (removed 2026-07-15, see `07_SMART_TRENDS.md` Layer 2). For bodyweight lifts, the gauge shows a single best plain-bodyweight rep count, also no longer decayed.
- **`SingleGoalGauge`** (custom goal, 2026-07-15, reworked into a log the same day): same track/fill visual, one tick at the **most recent entry** in the exercise's custom-goal log instead of 5 published tiers. Used when `Exercise.goalSource` resolves to `custom` — either because there's no published standard for that lift, or the user explicitly chose to override one that exists. A small "Standard"/"My Goal" chip toggle appears only when both a standard and a custom goal exist for the same lift; a "tune" icon opens `CustomGoalHistorySheet` — add a new labeled entry, browse/delete old ones, see `07_SMART_TRENDS.md` "Custom goals." The progress bar's fill is **always** the real true max/best rep count regardless of which goal source is active — the custom target only changes where the single tick sits, never what "current progress" means.
- **Data needed**: latest logged bodyweight (used internally only — still never shown as a raw number, per `00_UX_DESIGN.md`; not needed at all for the bodyweight-rep or custom-goal paths), gender and birth-year-derived age bucket (both new Settings fields, see `06_SCREEN_settings.md`), and either the exercise's mapped standard table or its `custom_goals` row.
- **Explicitly out of scope this round**: personalized short-term sub-goals (a "safe next PR to aim for" tailored to the user's own recent growth rate, sitting between their current PR and this main goal) — this turned out to be a re-skin of the Next Heavy Set box, see `07_SMART_TRENDS.md`.
- **"i" info tooltip** (`strength_goal`/`strength_goal_bodyweight` glossary entries) states plainly that published standards are commonly-cited-style approximate figures, gender/age adjusted, not a personally measured standard — same directional-generalization caveat pattern used for recovery windows and lean-mass-gain ranges elsewhere in this app. (No equivalent caveat needed for a custom goal — it's just whatever number the user typed in.)

**Category pills removed** from this screen — redundant with the Lifts list, per the user's call once they saw the page next to that list.

### Predicted-next-e1RM: `RangeIndicator` redesign
Previous version used a plain `Row(mainAxisAlignment: spaceBetween)` for the three labels, which only reads correctly when the values happen to be evenly spaced — not guaranteed once the confidence band stops being symmetric (see `07_SMART_TRENDS.md` for why today's fixed ±50lb band is a placeholder). Redesigned:
- The low↔high whisker span is inset from the card's full width by a fixed breathing-room padding (20% of the span on each side) rather than touching the edges.
- Each of the three labels (low/goal/high) is positioned via a `Stack` + `Positioned`, centered under its own point's actual pixel x-position — not assumed evenly spaced. This means an asymmetric band (goal off-center) will still line up correctly whenever the confidence calculation stops being symmetric.

### Notes — user-entered, replaces the curated "Overview" cues (2026-07-16)
The old `MuscleMap.liftOverview`/`LiftCue`/`CueKind` — 3 short icon-prefixed placeholder-quality cues per seeded lift (setup/motion/safety) — is **wiped entirely**, per the user's call: "I want the overview to be user entered." Replaced by `Exercise.notes` (free text, `null` until written) shown plainly under a "Notes" header, with a pencil icon that opens a bottom sheet (multi-line `TextField`, pre-filled with whatever's there, a single Save button) to write or edit it. Empty state: "No notes yet — tap the pencil to add your own." No curated content ships with any lift anymore, seeded or custom — this is entirely the user's own material (form cues, reminders, whatever they want), which sidesteps the "not meant to be final copy" caveat the old placeholder text always carried.

### Add/edit exercise — muscle selection (2026-07-16)
A **fine-grained, user-set muscle list** (`Exercise.targetMuscles`) now exists alongside the old curated `MuscleMap.liftMuscles` fallback (unchanged, still used for older seeded lifts that haven't had this set) — `MuscleMap.musclesFor` prefers `targetMuscles` when non-empty, falls back to the curated map, then to a broad-category guess, same priority order as before just with a new first rung. Set via `MuscleSelectorSheet` (`screens/lifts/muscle_selector_sheet.dart`) — the same front+back `BodyHeatmap` diagrams as the soreness map, but a plain toggle per muscle (no severity level, since this is a one-time "does this lift hit this muscle" input, not a repeated log) and **every muscle the package exposes**, not just the app's 5 broad soreness groups, since precision matters more than tap-speed here. Opened via a "Select Muscles" button on the Add/Edit sheet; on the edit path it persists immediately (there's no separate save step tied to it), pre-seeded with the exercise's *current* effective muscles (`MuscleMap.musclesFor`) rather than the raw stored field, so an older seeded lift with curated-but-unset muscles doesn't open to a blank-looking picker.

**Layout fix (2026-07-17): stacked full-width, not side-by-side.** The first version put front+back diagrams side by side at half width, same as the muscle-diagram card elsewhere on Lift detail — but smaller muscles were genuinely hard to tap accurately at that size, undermining the whole point of a muscle-level (not just region-level) picker. Now stacked full-width, front then back, same layout `SorenessBodyMapForm` already uses — bigger tap targets, and this is what actually makes fine-grained selection practical rather than just theoretically available.

**Movement patterns are explicitly not settable from this sheet.** `MovementPattern` exists purely to power the Workout Planner's backend pattern-pool matching (`10_WORKOUT_PLANNER.md`) — the user's call: it's a backend/seed-data concept, not a general-purpose exercise tag, and shouldn't be editable from the app at all (a future Excel-upload path is the intended way to manage it, not this sheet). A custom exercise added here simply carries no pattern and won't show up in the planner's pattern slots; editing an existing exercise never touches `patterns` either — whatever it already has (from seed data) stays untouched, since the field is just omitted from both the add and edit `copyWith`/constructor calls.

## Editing/deleting a logged session — implemented
`EditLiftSessionForm` (opened from either the Lift detail history or the Workouts tab) lets you change the date, edit/add/remove individual sets (reps/weight/RPE), edit notes, or delete the whole session with a confirm dialog. Sets are replaced wholesale on save (`LiftRepository.replaceSets`: delete all existing sets for that session, reinsert the edited list) rather than diffed — simpler, and fine at this data scale. Session-level fields (date, notes) update via `LiftRepository.updateSession` / `LiftSession.copyWith`.

**Exercise switch — added.** A picker at the top of the form now lets you reassign which exercise the session belongs to, added after a real gym mix-up — logging a set under the wrong lift used to mean deleting the whole session and retyping every set from scratch. `LiftSession.copyWith` gained an `exerciseId` param for this. **2026-07-15: became the same searchable `ExercisePickerField`** used by Log Lift (see `07_SMART_TRENDS.md` "Searchable exercise picker") rather than a pinned-plus-current dropdown — defaults to pinned + the session's current exercise, searches the full library once you type. The picker's first build always has real data loaded before rendering (a plain disabled text field shows briefly instead) — a fresh DB fetch never returns the same `Exercise` instance twice, so `_selectedExercise` is re-pointed at the freshly-loaded list's own instance rather than the original `widget.exercise` reference once options arrive.
