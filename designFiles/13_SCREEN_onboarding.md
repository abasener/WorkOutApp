# Screen: Onboarding (implemented 2026-07-20)

A short two-page survey shown before the main app on a genuinely fresh profile: a welcome page (basic info about the app, red "Next" button at the bottom), then a page to pick gender, enter a birth year, and enter a starting weight (all required). Finishing it drops straight into `RootShell` with a clean-feeling app: the entered profile info applied, the fixed defaults below set, and nothing else touched — no synthetic data, on either profile.

## Routing (`AppRoot`)
`main.dart`'s `home:` is `AppRoot`, not `RootShell` directly. `AppRoot` is a one-shot decision, not a listenable/rebuilding router: `UserProfile.onboardingComplete ? RootShell() : OnboardingFlow()`. That bool is resolved once per cold start inside `AppServices.init() → _loadPersistedSettings() → _resolveOnboardingFlag()`:
- If the profile's `app_settings` already has an `onboarding_complete` key, use it as-is.
- If not (every profile that existed before this feature shipped, plus any genuinely new one), check `DatabaseHelper.hasAnyPriorActivity()` — a **read-only** query across `app_settings`, `lift_sessions`, `bodyweight_log`, `metrics_log`, `cycle_log`, `cardio_sessions`, `hiit_sessions`, and custom (`is_seeded = 0`) `exercises`. Any row anywhere in that list means "this profile is already in use" — `onboardingComplete` is set true in memory and the flag is persisted (`onboarding_complete = 'true'`, one settings row written, nothing else touched) so it's resolved for good. Only a profile with *zero* rows across all of that falls through to actually showing `OnboardingFlow`. This is the safety-critical piece: onboarding can never retroactively interrupt a profile that already has real data or settings, on either the personal or demo side, and the check only ever reads before deciding whether to write one harmless flag row.

## The two pages (`OnboardingFlow`)
A `PageView` with `NeverScrollableScrollPhysics` (Next-button driven, not swipeable — keeps it a strictly linear two-step flow) and one shared button pinned to the bottom (`bottomNavigationBar`), which reads "Get Started" on the second page.
1. **Welcome** — the app's own turtle-with-dumbbells mark (2026-07-21, replaced a generic `Icons.bolt`; "terp" as in terrapin, matching the launcher icon), "Welcome to TerpinLift," a couple sentences on what the app is (navigation system, not a coach, per `00_UX_DESIGN.md`), three bullet points on what it tracks, and a line noting everything stays on-device and a couple quick questions are next. Its own "Next" button has nothing to validate, so it's always enabled and red. The logo is `assets/icon/foreground.png` (the same transparent PNG `flutter_launcher_icons` uses, newly declared as a real Flutter asset in `pubspec.yaml` so it's usable in-app, not just at icon-generation time) shown at 64px inside a `surfaceRaised` circular backdrop — the mark's black shell would otherwise nearly disappear against the app's near-black background.
2. **Profile** — Gender (two `ChoiceChip`s, Female/Male, defaults Female matching `UserProfile`'s existing default), Birth year (plain number field, **defaults pre-filled to "2000"**, editable), Starting weight (plain number field, hint just reads "Weight in lb," no example number — the user's explicit call: a suggested figure felt wrong, so the field starts genuinely blank rather than nudging toward any particular value). **All three are required** — birth year and weight can't be saved blank; the button below explains how that's enforced.

**"Get Started" is disabled until every field validates (2026-07-20).** `_canProceed` (a getter on `_OnboardingFlowState`) is false on the profile page until the birth year parses to an int in 1900-current-year AND the weight parses to a positive number — both text controllers carry a listener that triggers a rebuild on every keystroke so this updates live. While disabled, the button renders in a neutral, non-red style (`AppColors.surfaceRaised` background, muted text, `onPressed: null`) so it visually reads as blocked rather than just inert; once both fields validate it flips to the normal red/white accent style and becomes tappable. Gender never blocks it — a `ChoiceChip` default is always a selected value, there's no "unset" state for it the way there is for a blank text field.

## Finishing (`AppServices.completeOnboarding`)
Applies, in order:
1. `setGender` (from the page).
2. `setBirthYear` (parsed int — by the time this runs the button's own validation already guarantees it's in range).
3. `setStepsGoal(7000)`, `setWeightUnit(WeightUnit.lb)`, `setHideWeight(false)` — the three fixed "clean build" defaults the user asked for, applied regardless of what the survey asked (gender/birth year/weight are the only things actually asked; units/steps-goal/hide-weight are just reset to sensible starting points).
4. Logs the entered starting weight as a real `BodyweightEntry` for today.
5. `UserProfile.onboardingComplete = true`, persisted, `signalReload()`. `OnboardingFlow` then does its own `pushReplacement` into `RootShell` — not left to `AppRoot`, which is only consulted at the two points described above (cold start, and the demo-reset restart below).

**Never generates synthetic history, on either profile (revised 2026-07-20).** Earlier this called `TestDataService.load()` for the demo profile so "Reset Demo Data" ended on a fully populated app; the user's own follow-up call reversed that — finishing onboarding should leave the demo profile genuinely empty too, "so the app is empty... this will help me see what a new user sees." See `loadSampleDemoData` below for the separate, explicit way to fill it back in afterward.

Because every step routes through the same `AppServices` setters (`setGender`/`setBirthYear`/etc.) the rest of the app already uses, `completeOnboarding` writes into whichever profile is currently active — no profile-switching logic lives in the onboarding screens themselves. This is what lets the exact same flow serve both a real first launch (active profile: personal, the only option before demo is ever touched) and the demo-preview path below (active profile: demo, deliberately never switched away from) without any special-casing.

## Testing it: "Reset Demo Data" as an onboarding + empty-state preview
See `06_SCREEN_settings.md`'s Reset Demo Data entry for the button-level detail. In short: pressing it clears the demo profile's settings (`SettingsRepository.clearAll`) **and wipes its logged data** (`DatabaseHelper.wipeEverythingAndReseed` — lift/cardio/HIIT/bodyweight/metrics/cycle cleared, exercise library reseeded, no synthetic history), both scoped to whichever database `AppServices.settings`/`db` are currently bound to, which the button's own `!_inDemoMode` disable-guard plus `resetDemoDataToOnboarding`'s own profile check both ensure is the demo file. Then it flips the onboarding flag and re-enters through `AppRoot` — landing back on `OnboardingFlow` exactly like a fresh install would. Finishing the survey drops into a genuinely empty `RootShell` (per the revision above), which is the point: this is how "what does a new user see" gets reviewed without touching the personal database file, which `ProfileManager` keeps as a completely separate file from demo's on disk — there is no code path in this feature that opens or writes to the personal file while the demo profile is active.

**`loadSampleDemoData` — filling the empty demo app back in.** A separate Settings button ("Load Sample Data," next to "Reset Demo Data," same demo-only enable guard) that just calls `TestDataService.load()` directly — no settings touched, no onboarding, no flag changes. This is the explicit "I can load in the demo data if I want" step now that reset/onboarding no longer does it automatically.

## Known gaps
- No skip/back button — the two pages are the whole flow, and there's no way to bail into the app without finishing them (matches "short entry survey," not meant to be a heavyweight setup wizard).
- No re-entry point from Settings for the personal profile — once a personal install's onboarding is complete (or grandfathered in), there's no button to see the survey again the way Reset Demo Data provides for demo. Not asked for; the demo-reset path is the intended way to review/test it.
