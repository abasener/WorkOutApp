# Screen: Settings

## Dev mode (2026-07-21)
Everything demo-related — the Personal/Demo switcher, Reset Demo Data, Load Sample Data — is gated behind a hidden "dev mode" flag, off by default for any real install. The idea: none of this should be reachable by an actual end user poking around Settings, but it's genuinely useful for testing/reviewing the app (onboarding preview, sample data, etc.), so it stays fully available behind a deliberately-obscure gesture rather than being deleted or built as a separate debug flavor.

- **Storage** (`DevModeManager`, `lib/data/dev_mode_manager.dart`) — a plain marker file (`dev_mode.txt`, `"1"`/`"0"`), same pattern as `ProfileManager`'s active-profile flag file: readable at startup before any profile database is opened, and — critically — **not** inside either `app_settings` table, so it can never be reset by a demo wipe/reset and doesn't need to be duplicated per profile. `AppServices.devModeEnabled` (a `ValueNotifier<bool>`) mirrors it in memory for reactive UI.
- **Unlocking it — long-press, not a visible toggle.** Settings' "Reset Data" button (see below) is the hidden entry point: a normal tap does its usual job (confirm dialog, then wipe), but a **long-press** opens a plain numeric-code dialog. Typing `24` and confirming calls `AppServices.setDevMode(true)`; anything else (wrong code, Cancel) just closes the dialog with no feedback either way — an accidental long-press by a real user should look like nothing happened, not hint that a hidden feature exists.
- **What appears once unlocked** — a new "Developer Tools" section, gated by a `ValueListenableBuilder<bool>` on `devModeEnabled` (`SizedBox.shrink()` when off): the Active data set switcher (moved here from its own top-level section), the Reset Demo Data / Load Sample Data card, and a plain "Dev mode" `Switch` (defaults on, since this section only renders when it's already on) for turning it back off without repeating the long-press gesture — added specifically so testing the off-state doesn't require re-discovering the hidden gesture every time.
- **Turning dev mode off auto-returns to Personal.** If the demo profile happened to be active when dev mode gets switched off (`AppServices.setDevMode(false)`) or at the next cold start (`AppServices.init`, in case a previous session left it there), it switches back to Personal immediately — the code doesn't bother explicitly "disconnecting" the demo profile beyond that, since once its controls are hidden there's no way to reach it or do anything with it regardless of which file happens to be technically open underneath.
- **Reset Data** (renamed from "Wipe Data") — same confirm-dialog-then-wipe behavior as before (see below), always visible regardless of dev mode, and doubles as the long-press entry point described above.

## Implemented
- **Data set: Personal / Demo toggle** — a pill switch, backed by two entirely separate SQLite files (`terpinlift_personal.db` / `terpinlift_demo.db`, see `01_DATA_MODEL.md` "Personal vs. demo data set"), not a filter over one shared database — so switching can never mix or overwrite the other set. Switching to Demo always reseeds a clean synthetic set first (confirm dialog explains this) — toggling off and back on is the "start over" gesture. Switching to Personal never touches anything, just reopens that file as-is. The active choice persists across restarts via a plain marker file (`ProfileManager`), independent of either database. **Hidden behind dev mode as of 2026-07-21** — see above.
- **Profile: Gender toggle (Female/Male)** — defaults to Female (matches how this app was framed from the start), persisted in `app_settings` (`gender` key), read via `UserProfile.gender`. Feeds the bodyweight-ratio strength-standard Goal gauge on Lift detail (`07_SMART_TRENDS.md`) — not used or shown anywhere else.
- **Profile: Birth year** (plain number field, validated 1900–current year) — persisted in `app_settings` (`birth_year` key). Converted to a broad `AgeBucket` (`UserProfile.ageBucket`: under-20 / 20s / 30s / 40s / 50s / 60+) rather than an exact age, per the user's call — a bucket-based multiplier on the strength standards, not a precise age-graduated formula. Unset defaults to the 20s/reference bucket (no age adjustment) rather than blocking the Goal feature.
- **Units toggle (lb/kg)** — a pill switch; persisted in `app_settings` (`weight_unit` key). All weight is stored canonically in lb; this only controls display via the shared `Units` helper (see `00_UX_DESIGN.md`).
- **Hide my weight** — a switch in the same Units card; persisted in `app_settings` (`hide_weight` key). Masks **only the user's own bodyweight** — the Metrics weekly-bodyweight chart axis and the Days-tab bodyweight rows — as a masked "---lb"/"---kg" placeholder via `Units.formatMaskable`; trend shapes still show, just not the printed number. Lift weights (squat, bench, e1RM/PR, Strength Goal gauge, session history) are **never masked** — they always use `Units.format` — since the original implementation over-applied `formatMaskable` to those too, which was a bug (bodyweight-privacy intent, not a general weight-privacy toggle) fixed after on-device testing surfaced the miscommunication. Entry/edit forms are deliberately unaffected (you need the real number to log or correct one). Off by default, matching prior behavior.
- **Steps goal** — a plain number field in its own "Goals" card; persisted in `app_settings` (`steps_goal` key, `UserProfile.stepsGoal`), defaults to 10,000. Was hardcoded in `WeekRings` (Home's week-ring strip, `02_SCREEN_home.md`); now the only consumer reads this setting instead.
- **Export data** — dumps `BackupService._tables` (`exercises`, `lift_sessions`, `lift_sets`, `bodyweight_log`, `metrics_log`, `cycle_log`, `app_settings`) from the **active profile's** database to a JSON file (`terpinlift_export.json` for Personal, `terpinlift_export_demo.json` for Demo — separate filenames so one can never overwrite the other), still written to the app's private documents folder first (so Import keeps working the same way, below) but now **also opens the OS share sheet** (`share_plus`, `SharePlus.instance.share`) so it can actually be emailed, saved to Drive, saved to Files, etc. — the original version only reported the internal path in a snackbar, which on Android is inside app-private storage with no normal way to browse to it; the user correctly called this out as "not the way I want it done, it should be more like a download."
  - **Known gap, earmarked 2026-07-17, not fixed yet:** `_tables` predates several newer features and doesn't include `progress_photos`, `custom_metrics`, `custom_metric_entries`, `custom_goals`, `planned_sessions`, `workout_templates`, or `workout_template_days` — none of that data is in the export/import round-trip today. Progress photos specifically raise a second, bigger issue even once the table's added: `progress_photos` rows only store a file *path*, not the image itself, and this export is plain JSON (data only) — a real fix needs either bundling the actual image files alongside the JSON (a zip/archive format instead of a bare `.json`) or some other asset-inclusion story, not just a table-list change. The user asked for this to be remembered rather than built now, since she's unsure yet what the right approach is — revisit together when Export/Import next gets real attention, rather than a quick patch now.
- **Import data** — restores from that same profile-scoped export file (fresh-install restore, not a smart merge). Still reads from the fixed internal path, so re-importing only works from the same device/install that exported it — sharing the file out (above) doesn't currently create a way to import a *different* file back in; a real "pick a file to import" flow is a follow-up if that's ever needed.
- **Reset Data (renamed from "Wipe Data" 2026-07-21, still `_wipeData`/`wipeLoggedData` under the hood)** — confirm dialog on tap, then deletes all logged lifts/cardio/HIIT/bodyweight/metrics/cycle entries from the **active profile only** but keeps its exercise list intact. **Always visible**, dev mode or not — see "Dev mode" above for why, and for the long-press-for-a-code behavior layered onto the same button. **Bug fixed (2026-07-20):** cardio and HIIT sessions were never included — `wipeLoggedData` only ever cleared `lift_sets`/`lift_sessions`/`bodyweight_log`/`metrics_log`/`cycle_log`, so a "wipe" left every logged cardio session and HIIT workout behind despite the button's own description. Now also deletes `cardio_sessions`/`hiit_sessions`, which cascades to `cardio_entries`/`hiit_slots` (`PRAGMA foreign_keys = ON`).
- **Reset Demo Data (2026-07-20: now routes through onboarding into an empty app; dev-mode-gated 2026-07-21)** — lives in the Developer Tools section, only enabled while Demo is the active data set (switch to it above first, and `AppServices.resetDemoDataToOnboarding` independently no-ops if it's somehow called while Personal is active, a second guard behind the disabled button). Confirm dialog, then: clears every stored setting (`SettingsRepository.clearAll`) **and every logged entry** (`DatabaseHelper.wipeEverythingAndReseed` — lift/cardio/HIIT/bodyweight/metrics/cycle cleared, exercise library reseeded, no synthetic history generated) for the demo profile, both against the **demo database file only**, then flips `UserProfile.onboardingComplete` to false and navigates to `AppRoot`, which shows `OnboardingFlow`. Finishing that survey (`AppServices.completeOnboarding`) applies the entered gender/birth year/starting weight and the fixed post-onboarding defaults (7,000 step goal, lb, weight shown) and drops into `RootShell` — **genuinely empty**, not re-populated with synthetic history. This is deliberate (revised same day from an earlier version that auto-regenerated sample data): the point of this button is to show "what does a new user actually see," which a pre-filled app doesn't demonstrate. Personal data is a different file and is never touched by any part of this. Includes the same `cardio_sessions`/`hiit_sessions`-clearing fix as Reset Data above (they'd otherwise leave orphaned rows behind every reset).
- **Load Sample Data (new, 2026-07-20; dev-mode-gated 2026-07-21)** — sits next to Reset Demo Data in Developer Tools, same demo-only enable guard. Confirm dialog, then `AppServices.loadSampleDemoData()` — just `TestDataService.load()`, nothing else: no settings touched, no onboarding, no flag changes. The explicit, on-demand way to fill the (now-empty-by-default) demo profile with a fresh ~2 months of made-up history, separate from resetting it.

- **About card (refreshed 2026-07-21)** — was a one-line "personal strength and recovery tracker" plus the cycle-privacy note, stale since HIIT/cardio/custom metrics/onboarding all shipped after it was written. Now names the actual current feature set (lifts, cardio, HIIT, steps/sleep/soreness/weight/custom metrics) and the local-only/no-accounts fact, still gender-gated to append the cycle-privacy line for `Gender.female` only.
