# Screen: Settings

## Dev mode (2026-07-21)
Everything demo-related — the Personal/Demo switcher, Reset Demo Data, Load Sample Data — is gated behind a hidden "dev mode" flag, off by default for any real install. The idea: none of this should be reachable by an actual end user poking around Settings, but it's genuinely useful for testing/reviewing the app (onboarding preview, sample data, etc.), so it stays fully available behind a deliberately-obscure gesture rather than being deleted or built as a separate debug flavor.

- **Storage** (`DevModeManager`, `lib/data/dev_mode_manager.dart`) — a plain marker file (`dev_mode.txt`, `"1"`/`"0"`), same pattern as `ProfileManager`'s active-profile flag file: readable at startup before any profile database is opened, and — critically — **not** inside either `app_settings` table, so it can never be reset by a demo wipe/reset and doesn't need to be duplicated per profile. `AppServices.devModeEnabled` (a `ValueNotifier<bool>`) mirrors it in memory for reactive UI.
- **Unlocking it — long-press, not a visible toggle.** Settings' "Reset Data" button (see below) is the hidden entry point: a normal tap does its usual job (confirm dialog, then wipe), but a **long-press** opens a plain numeric-code dialog. Typing `24` and confirming calls `AppServices.setDevMode(true)`; anything else (wrong code, Cancel) just closes the dialog with no feedback either way — an accidental long-press by a real user should look like nothing happened, not hint that a hidden feature exists.
  - **Crash fixed on-device (2026-07-21): "A TextEditingController was used after being disposed," whole app went red-screen.** The code dialog's `TextEditingController` was manually disposed immediately after `showDialog` resolved (right after typing the code and tapping "Unlock") — but the dialog's own exit-transition animation keeps its `TextField` mounted/rebuilding for a few more frames after the `Future` completes, so disposal raced that animation. Fixed by simply never disposing this controller — it's a short-lived, one-off controller scoped to a single dialog invocation, not a `StatefulWidget`'s own field with a real lifecycle to hook `dispose()` into, so leaving it for the garbage collector is the standard, safe pattern here (unlike `_birthYearController`/`_stepsGoalController`, which are real fields correctly disposed in `State.dispose()`).
- **What appears once unlocked** — a new "Developer Tools" section, gated by a `ValueListenableBuilder<bool>` on `devModeEnabled` (`SizedBox.shrink()` when off): the Active data set switcher (moved here from its own top-level section), the Reset Demo Data / Load Sample Data card, and a plain "Dev mode" `Switch` (defaults on, since this section only renders when it's already on) for turning it back off without repeating the long-press gesture — added specifically so testing the off-state doesn't require re-discovering the hidden gesture every time.
- **Turning dev mode off auto-returns to Personal.** If the demo profile happened to be active when dev mode gets switched off (`AppServices.setDevMode(false)`) or at the next cold start (`AppServices.init`, in case a previous session left it there), it switches back to Personal immediately — the code doesn't bother explicitly "disconnecting" the demo profile beyond that, since once its controls are hidden there's no way to reach it or do anything with it regardless of which file happens to be technically open underneath.
- **Reset Data** (renamed from "Wipe Data") — same confirm-dialog-then-wipe behavior as before (see below), always visible regardless of dev mode, and doubles as the long-press entry point described above.

## Implemented
- **Data set: Personal / Demo toggle** — a pill switch, backed by two entirely separate SQLite files (`terpinlift_personal.db` / `terpinlift_demo.db`, see `01_DATA_MODEL.md` "Personal vs. demo data set"), not a filter over one shared database — so switching can never mix or overwrite the other set. Switching to Demo always reseeds a clean synthetic set first (confirm dialog explains this) — toggling off and back on is the "start over" gesture. Switching to Personal never touches anything, just reopens that file as-is. The active choice persists across restarts via a plain marker file (`ProfileManager`), independent of either database. **Hidden behind dev mode as of 2026-07-21** — see above.
- **Profile: Gender toggle (Female/Male)** — defaults to Female (matches how this app was framed from the start), persisted in `app_settings` (`gender` key), read via `UserProfile.gender`. Feeds the bodyweight-ratio strength-standard Goal gauge on Lift detail (`07_SMART_TRENDS.md`) — not used or shown anywhere else.
- **Profile: Birth year** (plain number field, validated 1900–current year) — persisted in `app_settings` (`birth_year` key). Converted to a broad `AgeBucket` (`UserProfile.ageBucket`: under-20 / 20s / 30s / 40s / 50s / 60+) rather than an exact age, per the user's call — a bucket-based multiplier on the strength standards, not a precise age-graduated formula. Unset defaults to the 20s/reference bucket (no age adjustment) rather than blocking the Goal feature.
- **Units toggle (lb/kg)** — a pill switch; persisted in `app_settings` (`weight_unit` key). All weight is stored canonically in lb; this only controls display via the shared `Units` helper (see `00_UX_DESIGN.md`).
- **Hide my weight** — a switch in the same Units card; persisted in `app_settings` (`hide_weight` key). Masks **only the user's own bodyweight** — the Metrics weekly-bodyweight chart axis and the Days-tab bodyweight rows — as a masked "---lb"/"---kg" placeholder via `Units.formatMaskable`; trend shapes still show, just not the printed number. Lift weights (squat, bench, e1RM/PR, Strength Goal gauge, session history) are **never masked** — they always use `Units.format` — since the original implementation over-applied `formatMaskable` to those too, which was a bug (bodyweight-privacy intent, not a general weight-privacy toggle) fixed after on-device testing surfaced the miscommunication. Entry/edit forms are deliberately unaffected (you need the real number to log or correct one). Off by default, matching prior behavior.
- **Steps goal** — a plain number field in its own "Goals" card; persisted in `app_settings` (`steps_goal` key, `UserProfile.stepsGoal`), defaults to 10,000. Was hardcoded in `WeekRings` (Home's week-ring strip, `02_SCREEN_home.md`); now the only consumer reads this setting instead.
- **Export data (2026-07-21: switched to an Excel workbook, and widened to every table)** — writes an `.xlsx` file (`excel` package, new dependency) from the **active profile's** database, one sheet per table, a header row of the exact snake_case DB column names, then one row per record (`terpinlift_export.xlsx` for Personal, `terpinlift_export_demo.xlsx` for Demo — separate filenames so one can never overwrite the other). Then opens the OS share sheet (`share_plus`) same as before, so it can be saved to Drive, emailed, saved to Files, etc. **Why the format change:** the user's own reasoning — JSON is much harder for a non-programmer to read than a spreadsheet, even though the data still uses internal ids/column names rather than anything prose-like ("not expecting an English-based output... just a better format for the average non-programmer"). Sheet names are Title Case for a clean set of tabs (`BackupService._exportTables`, e.g. `hiit_slots` → "HIIT Slots"); the header row inside each sheet stays exact snake_case DB column names on purpose, since that's what a future import needs to stay unambiguous, not something meant to read as prose.
  - **`BackupService._exportTables` now covers all 19 tables**, not just the original 7 — `cardio_sessions`/`cardio_entries`, `hiit_sessions`/`hiit_slots`, `custom_metrics`/`custom_metric_entries`, `custom_goals`, `progress_photos`, `planned_sessions`, `workout_templates`/`workout_template_days`, and `todo_items` all newly included alongside the original `exercises`/`lift_sessions`/`lift_sets`/`bodyweight_log`/`metrics_log`/`cycle_log`/`app_settings`. `app_settings` alone already covers gender, birth year, units, hide-weight, steps goal, Home/Metrics layout order, and the onboarding-complete flag — every plain setting lives in that one table already, nothing else needed adding for "settings."
  - **`progress_photos` removed from export entirely (2026-07-20)** — was metadata-only (a row's `file_path` points at an image in this device's own private storage, which a spreadsheet can't carry along with it), and stayed there as a known gap while embedding the actual image was still an open question. Checked the `excel` package's source directly: it has no image/drawing support at all, so embedding photos in cells isn't possible with this dependency. Rather than keep shipping metadata rows with dead `file_path` references that resolve to nothing after a restore, the user's own call was to drop the table from backup altogether instead.
  - **Verified via a round-trip smoke test** (encode then `Excel.decodeBytes` the same bytes, outside the app) rather than a unit test — this codebase has no sqflite-backed test scaffolding yet (a broader gap, not specific to this feature), so correctness here was confirmed by exercising the exact `CellValue`/`appendRow`/`encode` API surface directly with representative int/double/string/null values instead.
  - **Bug fixed (2026-07-20): a genuine export produced a workbook that failed to re-import, surfacing as "not a valid spreadsheet."** Root cause was in the `excel` package itself, confirmed with a throwaway script: it happily *writes* a `double` via Dart's own `toString()`, but its own reader can't parse that representation back for `NaN`, `Infinity`, or any value far enough from zero to trigger scientific notation (`1e-7`, `1e20`, etc.) — `Excel.decodeBytes` throws a `FormatException` on the very first such cell, which poisons the entire import over one stray value (e.g. a rate/average computed from a zero-length duration somewhere in months of real data, not something that would ever show up in a quick manual test). Fixed in `_toCellValue`: a double that's `NaN`, infinite, or whose `toString()` contains `'e'` is now written as `TextCellValue` instead of `DoubleCellValue` — SQLite's type affinity still accepts ordinary numeric text into a `REAL` column on the way back in, so normal values are unaffected and only the handful of pathological ones fall back to text.
  - **Export filename (2026-07-20): now `TerrapinLift_Export_<yyyy-mm-dd>[_demo].xlsx`** (was `terpinlift_export.xlsx`) — corrects the app-name spelling and adds the date so a user with several saved exports (Drive, email, Files) can tell them apart at a glance instead of guessing from a file's modified-date metadata.
  - **Bug fixed (2026-07-20): importing a genuine, unmodified export always failed with a `DatabaseException: UNIQUE constraint failed: app_settings.key`.** Every other table's real primary key is an autoincrement `id`, which import already skips so a fresh one gets assigned — a re-import can never collide with existing rows there. `app_settings` is different: it has no `id` at all, `key` (`gender`, `onboarding_complete`, ...) *is* its primary key, and every existing install already has rows for those same keys — so a plain `INSERT` was guaranteed to hit a constraint violation on the very first settings row and abort the whole transaction, regardless of what the rest of the file contained. This is why the error only ever showed up as a generic "not a valid spreadsheet" — the real `DatabaseException` was being swallowed by a bare `catch (_)` in `SettingsScreen._import`, which now includes the actual exception text in the error snackbar instead of a canned message, since that's what actually surfaced this. Fixed in both `importFromExcel` and `importFromJson`: every table still inserts (aborting on an unexpected collision), except `app_settings`, which now imports via `ConflictAlgorithm.replace` — restoring settings is supposed to overwrite the existing value for a given key, not fail outright.
  - **Import now replaces each table's data instead of inserting alongside it (2026-07-20)** — the user's own call: there's little use in an app like this for merging two datasets (e.g. two different periods of logged lifts), so a table the import file actually covers gets `DELETE FROM`'d immediately before its rows are inserted, rather than piling imported rows on top of whatever was already there (which previously meant re-importing the same file twice, or importing into a non-empty profile, silently duplicated every row — most visibly duplicate seeded exercises). Scoped per-table to only what's actually a recognized sheet/JSON key in the file being imported — an older or partial export missing some tables must never wipe a table it has no replacement data for. `app_settings` is excluded from the wipe (it already upserts by key) so a settings key added in a newer app version than the file predates isn't deleted just because the file says nothing about it. `BackupService.hasAnyLoggedData()` (checks every export table for at least one row, deliberately excluding `exercises` — always populated by seeded defaults — and `app_settings` — always has onboarding defaults) lets `SettingsScreen._import` skip the new "Replace current data?" confirmation dialog entirely on a genuinely fresh profile with nothing to lose, and only interrupt with it when there's real data the import is about to erase.
- **Import data (2026-07-21: updated to match the .xlsx export)** — `BackupService.importFromExcel` decodes the picked bytes (`Excel.decodeBytes`), matches sheet names against `_exportTables` (case-sensitive — a sheet renamed by hand isn't recognized) to find the real table, then matches each sheet's header row against that table's actual DB columns (`PRAGMA table_info`) rather than assuming position — an unrecognized/typo'd column is silently skipped per-cell rather than failing the whole row, and `id` is always skipped so autoincrement assigns fresh ones, same convention the JSON path already used. Type conversion is the fiddly part a spreadsheet round-trip needs that JSON never did: the `excel` package hands back typed `CellValue` subclasses (`IntCellValue`/`DoubleCellValue`/`TextCellValue`/`BoolCellValue`) when reading, not raw Dart values, so `_fromCellValue` pattern-matches each back to what SQLite expects (a `BoolCellValue` becomes `1`/`0`, since SQLite has no real boolean type); anything unexpected (a formula, a date typed in by hand) falls back to `toString()` rather than throwing. The user's own call on why this level of care is acceptable here despite being slower than JSON's free round-tripping: import is a rare, deliberate "my phone died" operation, not an everyday path — correctness matters far more than speed.
  - **`SettingsScreen._import` now dispatches between two formats** — `importFromExcel` (current) or `importFromJson` (an older export someone might still have, kept working rather than dropped) — detected by the picked file's extension, with a `PK` magic-byte check (the zip signature every `.xlsx` starts with) as an independent, always-checked second signal, not a fallback gated behind the extension being missing.
    - **Bug fixed on-device (2026-07-21): a fresh `.xlsx` export from this same app failed to import, surfacing as "not valid JSON."** `PlatformFile.extension` (the installed `file_picker` version) is implemented as `name.split('.').last`, which **never actually returns null** — a name with no dot at all just falls back to returning the whole name unchanged. The original detection logic was `extension == 'xlsx' || (extension == null && looksLikeZip)`, gating the byte-sniff fallback behind a condition (`extension == null`) that could never be true — so a file picked back from Drive/another app whose reported name didn't literally end in `.xlsx` (renamed, re-saved through another app, etc.) silently fell through to the JSON path no matter what its actual content was. Fixed by dropping the null-guard entirely: `extension == 'xlsx' || looksLikeZip` — the magic-byte check is authoritative on its own and doesn't need permission from the extension check to fire.
  - **File picker itself unchanged from 2026-07-20** — opens the OS's native file picker (`file_picker`) so the export can be picked from anywhere: Google Drive, Downloads, an email attachment already saved locally, another cloud provider's own picker integration, wherever it actually ended up after Export's share sheet sent it somewhere. `FileType.any` is used deliberately instead of filtering to an extension — some cloud providers report mime types inconsistently, and a strict filter risks the real file just not appearing in the picker at all; format is detected after reading instead.
  - **Verified via the same round-trip smoke test approach as Export** (no sqflite-backed test scaffolding in this codebase yet) — the `CellValue`-unwrapping logic in `_fromCellValue` was exercised directly against representative int/double/string/null/bool values outside the app, mirroring `_toCellValue`'s own earlier verification. The full `BackupService.importFromExcel` path (sheet matching, `PRAGMA table_info` column validation, the transaction/insert loop) reuses the same structural pattern the already-working `importFromJson` path uses, just swapping in typed-cell extraction for JSON's free type-preservation — not independently exercised against a real on-device SQLite database end to end, since standing up that harness was judged out of scope for this round; real confidence here should come from an actual on-device export → import round trip before relying on it for a real restore.
- **Reset Data (renamed from "Wipe Data" 2026-07-21, still `_wipeData`/`wipeLoggedData` under the hood)** — confirm dialog on tap, then deletes all logged lifts/cardio/HIIT/bodyweight/metrics/cycle entries from the **active profile only** but keeps its exercise list intact. **Always visible**, dev mode or not — see "Dev mode" above for why, and for the long-press-for-a-code behavior layered onto the same button. **Bug fixed (2026-07-20):** cardio and HIIT sessions were never included — `wipeLoggedData` only ever cleared `lift_sets`/`lift_sessions`/`bodyweight_log`/`metrics_log`/`cycle_log`, so a "wipe" left every logged cardio session and HIIT workout behind despite the button's own description. Now also deletes `cardio_sessions`/`hiit_sessions`, which cascades to `cardio_entries`/`hiit_slots` (`PRAGMA foreign_keys = ON`).
- **Reset Demo Data (2026-07-20: now routes through onboarding into an empty app; dev-mode-gated 2026-07-21)** — lives in the Developer Tools section, only enabled while Demo is the active data set (switch to it above first, and `AppServices.resetDemoDataToOnboarding` independently no-ops if it's somehow called while Personal is active, a second guard behind the disabled button). Confirm dialog, then: clears every stored setting (`SettingsRepository.clearAll`) **and every logged entry** (`DatabaseHelper.wipeEverythingAndReseed` — lift/cardio/HIIT/bodyweight/metrics/cycle cleared, exercise library reseeded, no synthetic history generated) for the demo profile, both against the **demo database file only**, then flips `UserProfile.onboardingComplete` to false and navigates to `AppRoot`, which shows `OnboardingFlow`. Finishing that survey (`AppServices.completeOnboarding`) applies the entered gender/birth year/starting weight and the fixed post-onboarding defaults (7,000 step goal, lb, weight shown) and drops into `RootShell` — **genuinely empty**, not re-populated with synthetic history. This is deliberate (revised same day from an earlier version that auto-regenerated sample data): the point of this button is to show "what does a new user actually see," which a pre-filled app doesn't demonstrate. Personal data is a different file and is never touched by any part of this. Includes the same `cardio_sessions`/`hiit_sessions`-clearing fix as Reset Data above (they'd otherwise leave orphaned rows behind every reset).
- **Load Sample Data (new, 2026-07-20; dev-mode-gated 2026-07-21)** — sits next to Reset Demo Data in Developer Tools, same demo-only enable guard. Confirm dialog, then `AppServices.loadSampleDemoData()` — just `TestDataService.load()`, nothing else: no settings touched, no onboarding, no flag changes. The explicit, on-demand way to fill the (now-empty-by-default) demo profile with a fresh ~2 months of made-up history, separate from resetting it.

- **About card (refreshed 2026-07-21)** — was a one-line "personal strength and recovery tracker" plus the cycle-privacy note, stale since HIIT/cardio/custom metrics/onboarding all shipped after it was written. Now names the actual current feature set (lifts, cardio, HIIT, steps/sleep/soreness/weight/custom metrics) and the local-only/no-accounts fact, still gender-gated to append the cycle-privacy line for `Gender.female` only.
