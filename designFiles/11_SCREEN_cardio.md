# Cardio (implemented 2026-07-19, revised same day)

"Light handling" of cardio — this app is a strength-training tracker first (lifts, powerlifting, bodybuilding), not a running/cycling app. Cardio gets a real backend of its own rather than being shoehorned into `lift_sessions`/`lift_sets` (reps/weight never meant anything for "how far did you run"), but deliberately stays simple: distance, duration, an optional resistance number, and a pair of goal gauges. No training-load modeling, no HR zones, no route maps.

## Data model
A cardio exercise is still just an `Exercise` row — tagged `ExerciseType.cardio` (via `equipmentTags`), same as any other equipment tag. What's new is a **parallel log table pair**, `cardio_sessions`/`cardio_entries`, mirroring `lift_sessions`/`lift_sets`' shape exactly (a session is the date+notes container; entries are the actual numbers, usually one per session but the schema allows more for interval-style cardio):
- `cardio_entries.distance_canonical` — meters for a real-distance exercise, or a raw floor count for a floors-unit exercise (see "Per-exercise distance units" below).
- `cardio_entries.duration_seconds` — plain integer seconds. Logged as a decimal "minutes" field in the entry forms, converted to seconds on save — no mm:ss text parsing needed for entry, just display (`CardioUnits.formatDuration`).
- `cardio_entries.load` — a **generic, unitless** resistance/incline/added-weight number (a rower's resistance level, a treadmill incline percent, a ruck's pack weight). Deliberately not run through any unit conversion, since it doesn't consistently mean "weight" — stored and shown exactly as entered. Labeled "Resistance (optional)" in the entry forms.
- `cardio_entries.rpe` — a plain 1-10 "how hard did that feel" effort scale, entered directly (**not** the lift form's "reps left" inversion, which doesn't make sense outside a set-based framing) — labeled "Effort (1-10)," 10 = hardest.
- `custom_goals` gained `target_distance`/`target_pace` columns alongside the existing `target_weight`/`target_reps` — same log-not-single-value table, same `CustomGoal` model, two more optional axes. A cardio exercise's goal log uses `target_distance`/`target_pace`; a lift's uses `target_weight`/`target_reps`; never mixed on one row.

### Per-exercise distance units (revised 2026-07-19)
The first cut used a single app-wide mi/mph-vs-km/kmh toggle (reusing the existing lb/kg setting). On review this didn't fit — a run tracked in miles, a row tracked in meters, and a stairs session tracked in floors all need to coexist, and pace (min/mile) matters far more than speed (mph) for most cardio. Reworked:
- `Exercise.cardioUnit` (new column, `DistanceUnit?` — miles/km/meters/floors) is the exercise's own designated display unit, set via the pencil-edit sheet (`AddExerciseSheet`, a `ChoiceChip` row shown only when the Cardio type tag is selected). Every logged entry and every goal for that exercise displays/converts through this one unit, so "Rowing Machine" always reads in meters even if the app-wide weight-unit toggle is on lb.
- **Per-entry unit picker.** `LogCardioForm`/`EditCardioSessionForm` show a small unit dropdown next to each effort's distance field, defaulting to the exercise's own unit but independently choosable per entry — a sprint logged in meters on an otherwise-miles Run still converts to that Run's one canonical number on save. Floors is excluded from this dropdown for non-floors exercises and vice versa (see below).
- **Canonical storage**: miles/km/meters are mutually convertible and always stored as meters (`CardioUnits.toCanonical`/`fromCanonical`, keyed off `DistanceUnit.metersPerUnit`). **Floors is deliberately not part of that conversion family** — a flight of stairs isn't a distance — so a floors-unit exercise's `distance_canonical` just holds the raw floor count, and its entries/goals never offer a unit picker at all (nothing to convert between).
- **Pace, not speed, for the goal gauge.** `CardioEntry`/`CardioSessionWithEntries` derive pace (`CardioUnits.paceSecondsPerUnit`, seconds per the exercise's display unit — e.g. "9:45/mi") rather than speed (mph). `CustomGoal.targetPace` stores this canonically as **seconds per meter** (or per floor), same basis the derived figure is computed on, so a goal and a logged result are always comparable regardless of which unit the exercise happened to be set to when either was entered. Floors-unit exercises get no pace goal at all — "pace up the stairs" wasn't asked for and the concept doesn't map cleanly. **`SingleGoalGauge` gained a `lowerIsBetter` flag** (plus a configurable `currentLabel`, since "True max" doesn't fit pace) to support this — the fill/tick positions mirror across the domain so faster (smaller) numbers still visually fill the bar toward "achieved," without needing a second gauge widget.
  - **A meters-unit pace bug was caught building demo data for Rowing Machine** — plain "seconds per meter" is always under a second, so pace displayed as a useless "0:00/m." `DistanceUnit` now has a separate `paceUnitMeters`/`paceSuffix` pair from the plain distance `metersPerUnit`/`suffix`: miles/km paces are per-mile/per-km as expected, but a meters-unit exercise's pace is per-**500m** (the standard rowing-split convention, e.g. "1:50/500m") instead of per-1m. Distance display/conversion is untouched — only pace uses this second mapping.
- Seeded defaults: Run/Ruck/Bike/General Cardio/Other Cardio → miles, Rowing Machine → meters, Stairs → floors.
- Migration: DB v19. `exercises.cardio_unit` added; `cardio_entries.distance_miles` renamed to `distance_canonical` and `custom_goals.target_speed` renamed to `target_pace` (both via `ALTER TABLE ... RENAME COLUMN`, since neither had any real user data yet — v18 having just shipped days earlier in this same round); `exercises.cardio_unit` backfilled by name for the 7 seeded cardio exercises. v18 (DB v18, same day) is unchanged as historical migration code — `cardio_sessions`/`cardio_entries` created fresh, new seeded cardio exercises backfilled by name (same "only insert if not already present" pattern as the v5 bulk-library backfill).

## Seeded exercises
Rowing Machine already existed (seeded pre-cardio-backend, historically logged through the lift reps/weight form — nothing forces it onto the new cardio flow retroactively, but going forward every cardio-tagged exercise, Rowing Machine included, logs through `LogCardioForm`/`cardio_sessions`). Added: **Run, Ruck, Bike, Stairs, General Cardio, Other Cardio** — broad categories/movement-pattern tags kept light (legs/core-ish where obviously true, empty for the two catch-alls) and deliberately **no muscle-map entries** (`MuscleMap.liftMuscles`) for the new ones — cardio isn't wired into the muscle-readiness/Primed-for-Growth engine, which is a deliberate scope boundary (see "Known gaps" below), not an oversight. A user can still tag a custom cardio exercise via `AddExerciseSheet`'s existing Type chips (`ExerciseType.cardio` was already selectable there).

## Screens
- **`LogCardioForm`** (`screens/quick_log/`) — the cardio counterpart to `LogLiftForm`: exercise picker restricted to cardio-tagged exercises, one row per logged effort (distance + unit dropdown / duration / resistance / effort, "add another effort" for interval days), date, notes, Done. A stopwatch icon next to the date (same slot `LogLiftForm`'s Calc button sits in) opens `SimpleTimerSheet`. Reachable from `QuickLogSheet`'s "Cardio" tile (`Icons.directions_run`) and from `CardioDetailScreen`'s "+".
- **`CardioDetailScreen`** (`screens/lifts/`) — a **deliberate fork** of `LiftDetailScreen`, not a parametrized shared screen (reps/weight/e1RM/RPE-trend prediction don't have a cardio equivalent worth forcing into the same code path). Sections: a 3-stat row (last trained / last distance / last pace), the same muscle-map+notes+video row `LiftDetailScreen` has (empty muscle map for exercises with no `MuscleMap` entry, same as any custom lift), a **Distance History** trend chart (`CenteredTrendChart`, each session's literal total distance, dot size encoding that session's peak resistance — same "encode a secondary fact as dot size" idea as the lift chart's rep-count dots, no prediction line since there's no formula predicting future distance), **two independent goal gauges** (Distance, Pace — each only shown if it has at least one logged goal, Pace hidden entirely for a floors-unit exercise, `current` is the all-time best single-session value for that axis — "Best distance"/"Best pace," never averaged/decayed, same convention `LiftDetailScreen`'s True Max uses), and a History list (session date, each entry's distance/duration/pace/resistance/effort, edit pencil).
- **`EditCardioSessionForm`** — mirrors `EditLiftSessionForm`: re-pick exercise/date, edit/add/remove entries (same per-entry unit dropdown as the log form — existing entries display/edit in the exercise's *current* unit, since only the canonical number is stored, not which unit it was originally entered in), delete the whole session. Also has the stopwatch icon.
- **`CardioGoalHistorySheet`** — mirrors `CustomGoalHistorySheet`'s "add, label, browse, delete" log shape, with a Distance/Pace `ChoiceChip` toggle (Pace chip hidden for a floors-unit exercise) instead of the lift sheet's implicit bodyweight/weight branch, since a cardio exercise can have both goal types active at once. Takes the whole `Exercise` (not just an id) so it knows which unit to label/convert with.
- **`SimpleTimerSheet`** (`widgets/`, new, shared) — a plain start/pause/reset stopwatch (`Stopwatch` + a 1-second `Timer.periodic` redraw tick), reachable from both `LogLiftForm` and `LogCardioForm`. Keeps the screen awake for as long as it's open (`WakelockPlus.enable()`/`disable()` in `initState`/`dispose`) and can optionally beep on a user-set minute interval (`SystemSound.play(SystemSoundType.alert)` — built into Flutter, no bundled audio asset), muteable via a switch for public settings. Deliberately **not** a background-survival timer — no notification, nothing persisted, closing the sheet loses the running time, same as closing a phone's stock stopwatch screen while it's not the frontmost app. Not wired to auto-fill the duration field (a possible future enhancement, not asked for this round).
- **Routing**: `exerciseDetailScreen(Exercise)` (`screens/exercise_detail_nav.dart`) is the one place that branches on `ExerciseType.cardio` to pick `CardioDetailScreen` vs. `LiftDetailScreen` — every nav call site (Lifts tab list + Workouts tab, Home's primed-lifts chips, the Workout Planner's pattern pool) goes through this instead of constructing `LiftDetailScreen` directly.
- **Lifts tab filter**: no new UI needed — `ExerciseType.cardio` was already one of the `_FilterSheet`'s "Type" chips and already sorted into the "Type" sort's priority order (`lifts_screen.dart`).
- **Home's week rings**: `AppServices.cardio.getAllWorkoutDates()` is unioned into the same date set `AppServices.lifts.getAllWorkoutDates()` feeds, so a cardio-only day still lights up the inner "worked out" fill.

## Known gaps / deliberate scope boundaries
- **Not wired into the readiness/Primed-for-Growth engine.** Cardio exercises carry no `MuscleMap` entries, so `ReadinessEngine`/`suggestPrimedLifts`/the muscle heatmap treat them as hitting nothing. Deliberate for v1 — revisit only if there's a real reason to (e.g. rucking under load meaningfully fatiguing legs/back).
- **Distance History has no prediction line** — unlike the lift trend chart's dashed e1RM-based projection, there's no cardio-equivalent formula being modeled; the chart is literal history only.
- **The Lifts tab's "Workouts" day-grouping tab stays lift-only** — cardio sessions don't appear there yet, only in Home's week rings and each exercise's own Cardio Detail history.
- **Load is unitless and unvalidated** — a rower's "resistance level 5" and a ruck's "35 lb" both just go in the same numeric field; no per-activity unit label. Fine for personal use.
- **Changing an exercise's `cardioUnit` after logging doesn't re-interpret old entries** — display simply re-converts existing canonical numbers through whatever unit is currently set. This is only a real problem if someone switches an exercise *into or out of* `floors` after logging real-distance entries (or vice versa), since floors isn't part of the conversion family — an edge case not guarded against, not expected to come up in practice (an exercise's unit is meant to be set once and left alone).
- **The timer doesn't feed the duration field.** Reading the stopwatch and manually typing the minutes into the entry is the current flow; auto-fill is a plausible follow-up, not built.
