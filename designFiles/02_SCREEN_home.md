# Screen: Home

The dashboard. First thing seen on open. Data-forward, per the icon → plot → words priority (see `00_UX_DESIGN.md`).

## Layout editing (implemented 2026-07-18, revised 2026-07-19)
An edit-pencil/checkmark toggle in the AppBar switches Home between normal view and **edit mode**: every section below becomes drag-reorderable (`SliverReorderableList`, a drag handle icon on each row's right edge starts the drag — the rest of the row stays inert, `IgnorePointer`-wrapped, so accidentally tapping into a card mid-edit isn't possible) and swipe-to-remove (`Dismissible`, swipe right-to-left, hides that section rather than deleting any underlying data). While editing, a "+" appears in the AppBar opening a list of addable widgets — every hidden single-instance section, plus **Strength Trend** and **Metric Trend**, both always offered since they're repeatable (see below). Each row in that list is `[icon] [name]` (`HomeWidgetIdKey.icon`, one per type — a weight for Strength Trend, a line-chart glyph for Metric Trend, a thermostat for Primed for Growth, a checklist glyph for Checklist, etc.) — added purely so the list reads as more than a wall of text. Newly added widgets are inserted at the **top** of the order, not the bottom, so they're immediately visible without scrolling. Order/visibility is one setting: an ordered list of `HomeLayoutItem` tokens (`home_widget_order` in `app_settings`, comma-joined — a token is `<HomeWidgetId>`, `<HomeWidgetId>:<exerciseId>` for Strength Trend cards, or `<HomeWidgetId>:<metricRef>` for Metric Trend cards) — anything single-instance from the enum not present is hidden; `null`/unset means "not customized yet," which falls back to every section in its original default order, with one Strength Trend card per zero-state active lift and **no** Metric Trend cards (opt-in only, no natural zero-state equivalent). Reordering/removing/adding persists immediately and calls `setState` right after the write completes (not after the full data-reload cycle that follows) — the previous version waited on `_load()`'s several repository queries to finish before the UI reflected the new order, which read as the dropped item's row snapping back to its old position for a moment before jumping to the real one.
- **Drag-and-InkWell fix**: `SliverReorderableList`'s default drag proxy (the floating copy shown while dragging) does **not** wrap the item in a `Material` ancestor, unlike the higher-level `ReorderableListView`. Any section containing an `InkWell` — only the Plan-a-session card, via `AppCard.onTap` — threw a "No Material widget found" error while it was the widget actively being dragged (visible as a scoped red error box in place of just that item, not the whole page). Fixed with an explicit `proxyDecorator: (child, ...) => Material(color: Colors.transparent, child: child)` on the `SliverReorderableList`.

## Strength Trend widgets (revised 2026-07-19)
What was originally one combined "Strength Trends" section (one header, multiple lift charts stacked under it, picked via a multi-select sheet) is now a **repeatable single-lift widget** — each Strength Trend card has its own header (the lift's name) and its own edit pencil, and the user can add as many as they want, in any order, interleaved with other sections. `HomeWidgetId.strengthTrends` is the type; `HomeLayoutItem.exerciseId` says which lift a given card tracks (`null` for every other, single-instance widget type). Adding one (via the "+" menu, always offered) or editing an existing one's lift (its own pencil) opens `StrengthTrendEditSheet` — a single-lift picker (already-used lifts excluded, so two cards can never silently track the same lift and collide) plus the shared "months of history" field (`HomeTrendSettings.months`, applies to every Strength Trend *and* Metric Trend card, not just the one being edited). **The edit pencil only shows while Home is in edit mode** — this is the first widget built under a new general rule: any per-widget "change what this tracks" control added from now on is edit-mode-gated, to keep editing a single deliberate mode rather than scattered pencils everywhere. This does **not** retroactively apply to the Checklist's edit pencil, which by design stays available outside edit mode (see below) — Checklist editing is managing your list's contents, not Home's layout, and the two were deliberately kept independent.

## Metric Trend widgets (implemented 2026-07-19)
The same repeatable-card pattern as Strength Trend, but for anything on the Metrics screen — Steps, Sleep, Weight, Workout Duration, or any custom metric. `HomeWidgetId.metricTrend`; `HomeLayoutItem.metricRef` is `'steps'` / `'sleep'` / `'weight'` / `'workoutDuration'` / `'custom:<id>'`. Adding or editing one opens `MetricTrendEditSheet` — same shape as the Strength Trend sheet (single-select list, already-used metrics excluded, shared "months of history" field), listing `MetricTrendOption`s (built-ins plus one per existing custom metric, each with its own icon). Deliberately **reuses the Metrics screen's own point-computation code** rather than reimplementing "what does this chart look like" a second time: `MetricChartPoints` (new, `lib/services/metric_chart_points.dart`) holds the point/formatter logic — raw entries for Steps/Sleep, weekly-averaged for Weight (same privacy rule as the Metrics screen: no single raw bodyweight reading ever directly exposed), derived planned-session/Track-Time span for Workout Duration, and the classes-aware y-axis label formatter for custom metrics — and both `MetricsScreen` and `HomeScreen` call into it. Home loads the same underlying queries the Metrics screen's Overview tab does (steps/sleep entries, bodyweight, lift + planned sessions for duration, custom metric definitions/entries) since Home is a separate screen/state and can't just read `MetricsScreen`'s. Rendered with the same `LabeledTrendChart` widget the Metrics screen cards use — no new chart code, just a new place to see one. A deleted custom metric that a card still points at reads as "no metric chosen" rather than crashing.

## Checklist (implemented 2026-07-18, revised 2026-07-19)
A small, fixed, user-edited list of recurring reminders ("bring water bottle to gym," "log sleep") — **not** a one-off task list. Each row: a circular tap-to-check box that fills and strikes through the text when checked, plus an optional reminder time shown as a small alarm-icon chip. **Daily reset needs no background job** — a row's "checked" state is just `TodoItem.lastCheckedDate == today`, so a new calendar day reads as unchecked automatically, and unchecking is just clearing that same field back to `null` (e.g. if you tapped it by mistake). If the app is left open across midnight, a 1-minute `Timer` in `TodoListCard` notices the date has rolled over and forces a rebuild — `isCheckedOn` was already correct the instant midnight passed, this just makes sure something actually triggers the redraw instead of waiting on an unrelated reload to happen to fire first.

An edit pencil on the card opens a batch editor (`TodoEditSheet`) with the same "edit the whole set at once" shape as a lift session's set-row editor: each row is a text field + a time button (`showTimePicker`, defaults to "None") + a remove (–) icon, plus an "Add another item" button at the bottom and one Save that persists the entire list in one call (`TodoRepository.replaceAll`) — existing rows keep their id (and thus their check state) when still present, anything removed is deleted, anything new is inserted.

**Reminder notifications** (`flutter_local_notifications` + `timezone`/`flutter_timezone`, both new dependencies) — an item with a time set gets a daily-repeating local notification at that time-of-day (`NotificationService.scheduleDaily`, `matchDateTimeComponents: DateTimeComponents.time`). Deliberately **inexact** scheduling (`AndroidScheduleMode.inexactAllowWhileIdle`) rather than requesting Android 12+'s separate "exact alarm" permission — that's a dedicated system-settings toggle, much heavier to ask for than the normal notification prompt, and "remind me around 7am" doesn't need to-the-second precision. Saving the edit sheet cancels every previously-scheduled id first, then reschedules fresh for whatever currently has a time — simplest correct way to handle edited/removed/added times without tracking a diff. Android gained `POST_NOTIFICATIONS` (the normal runtime prompt, requested the first time any item gets a time) and `RECEIVE_BOOT_COMPLETED` + two `flutter_local_notifications` receivers so a daily reminder survives a phone restart; `android/app/build.gradle.kts` gained core library desugaring (`isCoreLibraryDesugaringEnabled = true` + the `desugar_jdk_libs` dependency), which the plugin requires.

**Checking an item off silences today's reminder (2026-07-19).** `scheduleDaily` gained a `skipToday` flag — checking an item that has a time set reschedules its notification starting tomorrow instead of cancelling it outright, so the recurring daily reminder survives but doesn't nag again today now that it's done; unchecking (undo) reschedules normally, which can still fire today if the time hasn't passed yet. `TodoItem.reminderHour`/`reminderMinute` parse `timeOfDay` for these call sites without pulling a Flutter `TimeOfDay` into the otherwise-plain-Dart model.

## Contents (top to bottom) — implemented
Default order — customizable per-user since 2026-07-18, see "Layout editing" above; this is just the out-of-the-box `HomeLayoutSettings.defaultOrder`.

1. **Muscle status icons** (`MuscleStatusRow`) — replaces the old text-based Status cards, unifying the last piece that was still on the layer-1 recency heuristic instead of the compass. One icon per broad category (legs/back/chest/core/arms), icon *shape* carries which of 3 states applies, color carries urgency:
   - **Ready** (weight icon, green `AppColors.good`) — recovery window elapsed, or never trained; a soft "worth targeting today" nudge.
   - **Resting** (bed icon, muted grey `AppColors.textSecondary`) — still inside its typical recovery window from the last time it was trained. Deliberately *not* colored like a warning — this is the normal, expected state, nothing to act on.
   - **Overreaching** (warning-triangle icon, amber `AppColors.warn`) — RPE creeping up or e1RM dipping against its own recent average for that specific category, a stronger signal than plain rest. Computed **per category independently** (`ReadinessEngine.computeCategoryStatus`), per the user's explicit framing: legs being cooked/overreaching shouldn't block a nudge toward arms — there's no single blanket "take a rest day" verdict.
   - Tapping an icon opens a one-line plain-language explanation for that specific category. See `07_SMART_TRENDS.md` for the derivation.
2. **Plan a session** card — dark/idle by default, turns accent-colored with an elapsed-time readout while a Workout Planner session is active; tap opens Day Select (idle) or resumes the active `ActiveDayScreen`. See `10_WORKOUT_PLANNER.md`.
3. **Checklist** — see above.
4. **This Week rings** — one ring per day (last 7 days): outer arc fills by % of the daily step goal (`UserProfile.stepsGoal`, adjustable in Settings — `06_SCREEN_settings.md`, was hardcoded at 10,000), inner fill lights up if a workout was logged that day. Replaced an earlier plain checkmark strip — rings read as progress, not pass/fail.
5. **Primed for Growth** — the front+back per-muscle readiness heatmap (green scale), the app's actual "compass." Has an "i" info icon next to the title (`InfoTooltip(glossaryKey: 'readiness')`) with a short plain-language explanation (revised 2026-07-19 to two short sentences, down from a longer paragraph) and, as of the same date, the color-band legend as its footer (`ReadinessLegend`) — the legend used to live on the Home card itself as a temporary calibration strip, moved into the tooltip to keep the card lean. See `07_SMART_TRENDS.md` for the full formula and `08_GLOSSARY_AND_SCIENCE.md` for the tooltip copy.
   - **Good picks right now** (`PrimedLiftsRow`, revised 2026-07-19) — a single line of up to 4 tappable lift-name chips directly under the map, continuously auto-scrolling news-ticker style (loops seamlessly, no manual swipe needed) rather than wrapping to more lines, each chip tapping through to that lift's detail screen. Not a ranked "best lift" list and not a "you should do X" prescription — a **greedy weighted set-cover** (`ReadinessEngine.suggestPrimedLifts`) over every exercise's muscle coverage against the currently-primed muscles (readiness ≥ 0.6), so lifts that hit mostly-overlapping primed muscles don't both get suggested (e.g. Front Squat and Back Squat both hitting primed quads — only the one covering more of what's primed earns a slot; the other only appears if it adds primed muscles the first one missed). Candidates are also excluded outright if they'd work any muscle below the "Needs rest" band (readiness < 0.3) — a lift doesn't get suggested here just because it happens to also hit something sore or overreaching, even if its primed-muscle coverage is good. Empty state: "Nothing particularly primed right now."
6. **Training Split** — a 100%-stacked bar chart, one bar per workout day (rest days collapsed out, not calendar-spaced), showing that day's training weighted across body parts (legs/core/chest/arms/back) by RPE-sum. A "zoom out" view sitting above the per-lift trends — see `00_UX_DESIGN.md` "Training composition chart" for the full reasoning (why RPE-sum over the timer, multi-category attribution, color choices).
7. **Strength Trend cards** (customizable, repeatable — see "Strength Trend widgets" above) — one `CenteredTrendChart` (2:1 aspect) per card, e1RM not raw weight (see `08_GLOSSARY_AND_SCIENCE.md`), with the prediction extension on (last point at 75%, adaptive-degree polynomial trend continues). Zero state (never customized) seeds one card per pinned lift (capped to 4), falling back to recently-active lifts if nothing is pinned yet.
   - **Which lift, per card** — each card's own edit pencil (edit mode only), a single-lift picker excluding lifts other cards already track.
   - **How far back** — one shared field across every card, months, persisted as `home_trend_months` (default `6`). No upper bound enforced beyond a sanity clamp (1-999) — if the requested range goes back further than a lift actually has history, the chart just shows everything it has. Computed via real month subtraction (`DateTime(now.year, now.month - months, now.day)`), not a flat `× 30 days` approximation.
   - Tap-through to the lift's full detail isn't wired from these cards yet — only from the Lifts tab list and the primed-lifts chips.
   - **Metric Trend cards** (see "Metric Trend widgets" above) are the same repeatable-card idea, one per Steps/Sleep/Weight/Workout Duration/custom metric — not part of the default order (no zero-state list the way pinned lifts seed Strength Trend), purely opt-in via the "+" menu, and can be interleaved anywhere among the other sections once added.
8. Bottom nav bar (shared across all screens — see `00_UX_DESIGN.md` for the 5 destinations).

## Known gaps / next up
- No ordering/priority rule for the primed-lifts row beyond the greedy set-cover's own pick order (highest-coverage first) — hasn't needed one yet.
- Strength trend cards still aren't tappable through to the lift detail screen (only the Lifts tab list and primed-lifts chips are).
- The Strength Trend lift picker isn't searchable — fine at ~75 exercises with pinned-first sorting, may want a search field if the library keeps growing.
- Metric Trend cards aren't tappable through to the Metrics screen either, same gap as Strength Trend cards above.
- **HIIT timer** — named as wanted (2026-07-17), planned to live on Home "as a widget like the plan part" (i.e. its own `HomeWidgetId`) — not described in detail yet (work/rest intervals? rounds? sounds? a light cardio-logging backend?), explicitly next up after Home layout editing + Checklist (this round). Ask for details before starting.
- Checklist items are a flat list — no reordering *within* the edit sheet beyond the order rows were typed in (add/remove only, matching the "reps/sets input" pattern it was modeled on). Revisit if that turns out to matter once there's a longer real list.
